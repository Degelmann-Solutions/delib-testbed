# The common core of phase 3: layout and conventions

Phase 3 moves the quantities the ten products share into one core. This file describes where the core lives, how a product reaches it, what the core holds of the time axis, the tariff basis, the decrement rates, the policy counts, the cash flows, the expense inflation, the outputs and checks, the contract data and charges, the parameter files, the table factory and the formula literals, how the core quota is measured and bounded, and the conventions every core commit follows: commit trailers, the rules for measuring speed, the reason on a product override, and how a product's `UPSTREAM.md` states, against upstream, the files phase 3 changed; beside them, the process rules for stacked pull requests, which no test enforces. The tests that enforce the conventions are `tests/test_core.py`, `tests/test_tables.py` (the table factory), `tests/test_provenance.py`, `tests/test_core_quota.py` and `tests/test_baseline_deviations.py` (with the tool `tools/baseline_deviations.py`).

## Layout

- `core/Core/` is a modelx model of its own, with the spaces `Data`, `Projection` and `Tables`. It holds the shared cells and nothing product-specific: no product folder name, model name or model prefix appears anywhere under `core/` (grep test in `tests/test_core.py`). Because it is a readable model, the tests can load it without a product. Beside it, `core/param_usage.py` is a plain Python module, the static usage scan of the parameter reads (section "The parameter files"); `mx.read_model` of `core/Core` does not see it.
- `core/Core/Projection` is parameterized by `point_id`, like every product's `Projection`; its cells are written against the product's names (`data`, `tables`, `point_id`), which the product space provides. Its one Reference is the Module `types`, for the read-only `model_point()`; a product's `Projection` inherits it, under both engines.
- `core/Core/Data` holds the shared input loaders. Its cells use the product's References (`pd`, `model_point_file`, `param_file`, `mort_file`, `lapse_file`, `rentenfaktor_file`, `prem_freq_file`, `surplus_file`, `charge_file`, `hoechstrechnungszins_file`), which the product's `Data` defines; the core's `Data` defines no References. The scalar parameters are read through one lookup, `param("<item>")`, over the core file and the product's parameter files (section "The parameter files"). A loader reads its file at an index term (`mort_table_index()`, `lapse_table_index()`, `rentenfaktor_table_index()`, `surplus_table_index()`, `charge_table_index()`), the majority's index columns; a product whose file has other keys overrides the term with the literal it reads, not the loader.
- `core/Core/Tables` is the table factory (section "The table factory"). It takes no parameter and holds no contract data. Its References are `data`, the sibling `Data`, through which it reads the table parameters, and the Module `math`, for the exponential function of the law `gompertz_force`; a product's `Projection` reads it through the Reference `tables`, and no product space inherits it.
- Beside each loader `<reader>()` stands a dict cell `<reader>_dict()`, the same table as plain Python dicts, built once per model from the loader's DataFrame, so that a lookup that runs many times per contract reads a dict rather than `DataFrame.at`. The model point table is held by row, `model_point_table_dict()[point_id][column]`; every other table by column, `<reader>_dict()[column][key]`, keyed as the loader indexes it (a tuple for several index columns, in the file's order). A dict cell derives from its loader by name, so a product's override of the loader or its index term flows through, and it is built only where something reads it. The loaders keep returning their DataFrames. The core's `Projection` reads its lookups through the dict cells (`model_point`, `prem_freq`, `prem_freq_load`, `instalments`, `lapse_rate_base`, `hoechstrechnungszins`), keyed and wrapped as before, and its parameters (`omega_age`, `unisex_mix_male`, `expense_infl`, `roll_fwd_tol`, and `mort_table` in `mort_table_name`) through `param`; the products' own lookups move to them in entries 6–9 of the night-run epic.
- A product inherits every cell of the core's `Data` and `Projection`, also one it has no use for: a product without a lapse table still has a derived `lapse_table`, which nothing evaluates. `CORE_CELLS` in `tests/test_core.py` lists, for every cell in the core, the products that derive it and those that override it with a reason.

## How a product reaches the core

modelx `bases` work only inside one model, and each product is its own model. The core therefore enters each product's model folder as three symlinks next to the product's own spaces:

```text
products/<product>/<Model>/CoreData       -> ../../../core/Core/Data
products/<product>/<Model>/CoreProjection -> ../../../core/Core/Projection
products/<product>/<Model>/CoreTables     -> ../../../core/Core/Tables
```

The product's `__init__.py` lists `CoreData`, `CoreProjection` and `CoreTables` in `_spaces` (before `Data` and `Projection`), and its `Data` and `Projection` name the first two as bases in the serialized format of `mx.write_model`, one leading dot for a sibling space:

```python
_bases = [
    ".CoreProjection"
]
```

`mx.read_model` follows the symlinks, so the product stays a self-contained modelx model: `run.py` and the runner `tools/run_baseline.py` read it unchanged, under `--engine export` and `--engine modelx`. A product cell that the product space does not define is derived from the core; under `--engine modelx` the trace shows the core's formula. `Data.input_dir()` resolves from the product's model path, so a core cell reads the product's own input files.

`CoreTables` is a base of no space. The product's `Projection` reaches it through a Reference beside `data`, and the factory reaches the product's `Data` through its own Reference `data`, which resolves to the sibling `Data` in whichever model holds the space:

```python
tables = ("Interface", ("..", "CoreTables"), "auto")   # in the product's Projection
data = ("Interface", ("..", "Data"), "auto")           # in core/Core/Tables
```

So a product cannot override a cell of the factory, and the factory's cells are computed once per model, not once per `Projection[point_id]`: the runner's per-contract cleanup deletes the point's `Projection` item and leaves `CoreTables` as it is, under both engines.

`shutil.copytree` follows symlinks by default, so a scratch copy of a product folder (tests, `tools/measure_marginal.py`) holds real copies of the core spaces and runs the same way.

A checkout without symlink support (Windows without developer mode or `core.symlinks`) is not supported. Composing the core into the product at load time in `tools/` was probed as an alternative and not built (Moritz, 2026-10-25).

## What enters the core

A quantity enters the core when at least two products compute it by the same procedure, also with different parameters or with terms that differ. The core formula is then built from term cells with neutral defaults (0 or 1), and a product overrides only the terms it differs in, each with its reason; the rest of the formula still derives from the core. A switch in the core formula is a last resort, and a choice that depends on the contract belongs in the data (a model-point column or `param_tariff_type.csv`), not in the code. A procedure no other product shares stays in the product. A unification that changes results is a commit of its own, one quantity at a time (Moritz, 2026-10-26).

## The time axis

The core's `Projection` builds every clock cell from one term, `clock_offset_mth()`, the policy months completed at `t = 0`: 0 on the inception clock most products use, where `t` counts policy months from issue.

- `duration_mth(t) = clock_offset_mth() + t`, `duration(t) = duration_mth(t) // 12`, `policy_year(t) = duration(t) + 1`.
- `duration_y(k) = duration(12 k)`, `policy_year_y(k) = duration_y(k) + 1`, `age_y(k) = issue_age() + duration_y(k)`, `calendar_year_y(k) = issue_year() + duration_y(k)`; `age(t) = issue_age() + duration(t)` and `calendar_year(t) = issue_year() + duration(t)` read the same at a month.
- `k_start() = duration_init() - clock_offset_mth() // 12` and `t_start() = 12 k_start()`: an in-force point on the inception clock opens its frame at its duration, one on the valuation clock at 0.
- `horizon_age() = issue_age() + policy_term()`, the attained age at which the projection ends; `proj_len() = 12 (horizon_age() - issue_age()) - clock_offset_mth()`, the frame's exclusive end, and `proj_len_y() = proj_len() // 12`.
- `omega_age()`, the limiting age ω, the end age of the product's mortality table (a switched product overrides it with `omega_age_table()`; no tariff-type file holds the item any more): the first age nobody reaches, the death rate is 1 at ω − 1. `ret_age()` is the age at *Rentenbeginn* from the model point, `k_conv() = ret_age() - age(0)` its projection year (negative on a point already in payment) and `t_conv() = 12 k_conv()` its month.

The integer arithmetic is exact for any offset, `(12 d + t) // 12 == d + t // 12`, so a product on another clock overrides only the offset. Basis and Riester count `t` from the valuation date (`products/basisrente/model.md:54`) and override `clock_offset_mth = 12 duration_init`, BU counts from the valuation month and overrides it with `duration_mth_init`; every other clock cell derives. `issue_year()` reads the model point's column in every product with a calendar year; Riester's points carry it since entry 23 of epic-parameter-files, `2027 - duration_init`, where Riester overrode `issue_year() = valuation_year - duration_init()` until then. Every model point of these five products opens at the valuation date 1 January 2027, the core item `valuation_year`: `issue_year` plus its completed policy years is 2027 (`tests/test_core.py`, `test_every_model_point_opens_at_the_valuation_date`). The year of issue is a contract fact; to move the valuation date, a new-business point becomes new business of the new year and an in-force point keeps its year of issue and every contract fact and has its state (`pols_if_init` and every `*_init` balance) rolled forward by the model itself, its new projection reproducing the old one from the new valuation month (entry 23, where Basis' part-paid-up point 6 became two points, KLV gained `term_bonus_pp_init` and Basis and KLV pay the renewal commission in an in-force point's first projected year). On the valuation clock what counts projection years restarts at the valuation date: Basis' declared rate, *Überschussrente* uplift and expense inflation (`products/basisrente/technical-notes.md`, "Model point attributes"). BU floors `duration` at zero elapsed months before inception (a claim cohort's onset can precede it), and `policy_year` and `age` follow. The horizon is a term too: Basis, Riester, RV and Pflege end at `omega_age()` (lifelong annuities, a closed multi-state system), Index and FRV at `ret_age()` (the accumulation phase only), BU at its *Endalter* `cover_end_age()`; KLV and RLV derive the policy term. RV and Basis read ω off their table of the table factory since their switches, overriding `omega_age()` with `omega_age_table()`, the end age 121 of `dav2004r_proxy` (Basis read 122 off its file until then, so its frames are a year shorter); Riester reads it since its switch off the table of its role `annuity_mort_table`, `tables.end_age` of `dav2004r_proxy`, 121 (111 off its own mortality files until then, so its frames are ten years longer); Sofort reads it since its switch with `omega_age_table()`, 121 as its item gave, so its frames keep their length; Pflege, the last, reads it since its switch with `omega_age_table()`, the end age 110 of `pflege_aktive_proxy`, as its item gave, so its frames keep their length too. No tariff-type file holds the item `omega_age` any more; the core's `omega_age()` still reads it, unread by every product, until the commit after the last switch removes the old core cells.

Still per product: a frame start in months (`t_start` in FRV, Pflege and Sofort), Sofort's `proj_len` (two lives and the guarantee end) and second life (`issue_age`, `age`), and the deferments RV and Sofort state as years rather than an age (`aufschub_y`, `defer_years`), which are not `ret_age`. `CORE_CELLS` in `tests/test_core.py` lists every override.

## The tariff basis

The core's `Projection` holds the annual first-order equivalence that RLV and KLV share, and the parts of it that other products compute by the same procedure, built from term cells where the products differ in a part:

- `rechnungszins()` reads the model point's `rechnungszins` column. The rate used at conclusion applies for the whole term (§ 2 Abs. 2 DeckRV, `products/basisrente/sources.md:353`), so a book carries a stack of vintages and the rate is a contract attribute; every product with a *Rechnungszins* derives it (KLV, Riester, Sofort, RV, Index, Basis, RLV, BU and Pflege). RLV, BU and Pflege carry it as a model-point column, 1,00 % on every shipped point. `hoechstrechnungszins()` is the statutory cap in force at `issue_year()`, looked up by band in `hoechstrechnungszins_table()` (Sofort); KLV overrides it with its year-keyed `deckrv_table` (the split years at the higher rate). Both feed checks only.
- `disc_factor(y) = (1 + rechnungszins()) ** -y`, the annual factor to the start of policy year `y` (RLV, KLV), and `disc_factor_mth(t) = (1 + rechnungszins()) ** (-t / 12)`, the monthly factor (BU, Pflege). At `t = 12 y` the exponent `-t / 12` is exactly `-y`, so the two agree on year starts bit for bit.
- `mort_rate_tariff(t) = mort_load_tariff(t) * mort_rate_tariff_base(t)`, the first-order annual death rate in month `t`, and 1 where the base rate is 1, whatever the load (section "The table factory", "The derivation"), with `mort_load_tariff(t) = 1` and `mort_rate_tariff_base(t) = mort_rate_tariff_at_age(age(t))` (KLV and FRV, deriving it since their switches to the table factory, as they derive the whole cell: the core's unisex blend of the tariff's table, section "The decrement rates", for both the blend of `dav2008t_proxy` at a weight of 0.5, for KLV the rate its premium and its reserves stand on, for FRV the rate of its *Risikobeitrag*, charged a twelfth a month; until its switch FRV overrode `mort_rate_tariff_at_age(x)` with the read of its own unisex file). RLV derives it and overrides the load, the rating factor alone since its switch to the table factory (`(1 + m)` times the rating factor until then, on a second-order file), and the base, its unisex blend over two lives. RV derives it whole since its switch to the table factory: the unisex blend of `dav2004r_proxy` at the attained age and the birth year with the neutral load, the rate of its *Risikobeitrag* and of its column `mort_rate_guar`; until then it overrode the cell with the trend-projected rate of its own file on the model point's own sex. Sofort overrides it whole (generational, unisex, a second life; since its switch the blend of `dav2004r_proxy` at each life's birth year with the neutral load, read through its hook `mort_rate_gen`) and Pflege too (since its switch the margin `mort_actv_load_first` on the unisex blend of `pflege_aktive_proxy`, 1 where the blend is 1, read through its cell `tar_mort_rate_blend`, which serves its in-care tariff rate `tar_mort_rate_care` on the table of a care grade as well; the rest of its `tar_` family keeps its names).
- `unisex_mix_male()` from `param_tariff_type.csv` and `unisex_blend(q_m, q_f) = w q_m + (1 - w) q_f`, the unisex tariff blend (KLV, since its switch through the core's `mort_rate_tariff_at_age`, where its own cell of that name called the blend on the two rows of its file; Pflege, since its switch through its own `tar_mort_rate_blend`, on the two rates of the table of the active state or of a care grade, where it blended the rows of its file; BU since its switch to the table factory, for the tariff rates of both of its tables; RV since its switch, through the core's `mort_rate_tariff_at_age`, with a weight of 0.45; FRV since its switch, the same way, with a weight of 0.5, where its file was one unisex series; RLV since its switch, whose `mort_rate_blend` calls it once per life, on the two rates of the table of the life's smoker status, before the first-death rule over two lives; Riester since its switch, whose `ann_factor` calls it on the two rates of its annuitant table `dav2004r_proxy` at the birth year, with a weight of 0.45, where its file was one unisex series). Sofort reads the weight from `unisex_mix_male()` too, its row named `unisex_mix_male` as RLV's (were `mix_male` and `sex_mix_male`, 0.45 and 0.5), and since its switch calls the blend in its hook `mort_rate_gen` for the unisex `U`, on the two rates of `dav2004r_proxy` at a life's birth year, where its own `mort_rate_at_age` blended the rows of its file.
- `pols_tariff(y)`, the tariff survivorship entering policy year `y`, mortality only: 1 for `y <= 0`, then `pols_tariff(y - 1) * (1 - mort_rate_tariff(12 (y - 1)))`. It starts at issue also on an in-force point, since the tariff was struck then (RLV, KLV).
- `tariff_annuity()`, the premium annuity-due `sum(disc_factor(y) * pols_tariff(y))` over `y < prem_term()` (RLV, KLV), and `tariff_term_annuity()`, the same over the cover term weighted by `tariff_schedule(y)`, the base of a sum-related loading (RLV, KLV). Pflege overrides `tariff_annuity` with the expected present value of its monthly premium in units of `P` on its multi-state tariff ledger.
- The benefit values from terms with neutral defaults: `tariff_death_pv() = tariff_death_sum() * sum(disc_factor(y + 1) * pols_tariff(y) * tariff_death_load(y) * mort_rate_tariff(12 y) * tariff_schedule(y))` over `y < proj_len_y()`, `tariff_maturity_pv() = tariff_maturity_sum() * disc_factor(n) * pols_tariff(n)`, and `tariff_benefit_pv()` their sum. The defaults are 1, 1, 1 and 0. RLV overrides `tariff_schedule(y) = benefit_pp(12 y)` (the benefit schedule); KLV overrides `tariff_death_sum = sum_death()`, `tariff_death_load = rating_factor()` (the *Risikozuschlag* on the death leg only) and `tariff_maturity_sum = sum_assured()`. Pflege overrides `tariff_benefit_pv` with its *Pflegerente* on the multi-state ledger.
- `prem_net_level_pp() = tariff_benefit_pv() / tariff_annuity()`, the net level premium, a pricing quantity and never a cash flow (RLV, KLV, Pflege).

The term positions carry the byte identity: `x * 1.0` and `x + 0.0` are exact, reassociation is not. So a neutral term stands where the product's own factor stood (KLV's rating factor between `p` and `q`, the death sum outside the sum), and RLV's load stays one term, the rating factor since its switch to the table factory, `(1 + m) * rf` until then.

Core cells that call a cell the product defines, its hook into the chain: `beitragssumme_prem` calls `prem_gross_level_pp()` (KLV, Index) and `zillmer_amount` calls `alpha_rate()`, the product's *Zillmersatz* (KLV, FRV, Basis, RV, Pflege, Riester). A product without the hook inherits the core cell unused, as with every other core cell.

Still in the products, because unifying them changes results or adds a quantity (each a result-changing commit of its own, listed as open work):

- The gross premium. RLV, KLV, BU and Pflege solve the same first-order equivalence, `G = rho (A + cost PVs) / ((1 - beta) ae - alpha Beitragssumme - D)`, in different term orders and with different terms; it belongs in the core as a formula of term cells.
- The reserves. RLV's net reserve (`res_pp_at`, `res_zill_pp_at`) and KLV's (`res_net_pp`, `res_zill_pp`) are the same prospective procedure with different terms (maturity benefit, sum-insured schedule); KLV's paid-up and minimum reserves stay in KLV. RV's `av_pp` and Riester's `dk_pp` are the *Deckungskapital* rolled forward retrospectively, so the core's reserve has to offer the retrospective method beside the prospective one. BU and Pflege compute no *Deckungsrückstellung* (`products/berufsunfaehigkeit/technical-notes.md:1003`, `products/pflegerentenversicherung/technical-notes.md:32`); adding one is a new quantity.
- The annuity present values of Sofort, Riester and RV (`annuity_factor`, `ann_factor`, `annuity_due_factor`): one sum of discount factor times survivorship, differing in payment frequency, the Woolhouse deduction, the guarantee period and a second life.
- Sofort's and RV's inline discounting with `v = 1 / (1 + i)` raised to month fractions, `disc_factor_mth` in another float order.
- RLV's and BU's acquisition charges, `(z k) G` and `(a G) BS_u`: the zillmered amount in another float order than `zillmer_amount`.

Not suited to the core: the multi-state first-order engines of BU (`*_first` ledgers) and Pflege (`tar_*` ledgers) and Sofort's monthly two-life survivorship (`tariff_lives`), which are different procedures, not one procedure with different terms.

## The decrement rates

The core's `Projection` holds the second-order (best-estimate) decrement rates, each the annual rate of the policy year a month falls in beside the monthly rate the recursion applies, built from term cells with neutral defaults:

- `mort_rate_base(t) = mort_rate_at_age(age(t))`, the annual table death rate before the best-estimate factor. `mort_rate_at_age(x)`, the table rate at an attained age, is a core cell since the table factory's scaffold: `mort_rate_table(sex(), x)`, the rate of the tariff's table on the model point's own sex (the hooks, below). Index, BU, RV, KLV, FRV, Basis, Riester and Pflege derive it since their switches to the factory, Index the first (RLV, the sixth switched product, overrides it with its own hook, below; Sofort, the ninth, inherits it unused and reads the factory in a hook of its own for each of two lives): their death rates are those of the table the item `mort_table` names, for BU the rates of its active lives and its run-off, for RV and Basis those of the generational table at the birth year, for KLV the rates its file held, for FRV the rates of the own sex below its best estimate, where its unisex tariff file stood, for Basis the own sex's where its file was one unisex series, for Riester those of its accumulation, the period table read without a birth year through its override of `mort_rate_table`, where its file was one unisex series with an ω guard, for Pflege, the tenth and last, those of its active lives, `pflege_aktive_proxy` without a factor, where its own file stood. Sofort's override, with other arguments, went with its switch, and Pflege's, the read of its file at `(sex(), x)`, with its. `mort_be_factor() = 1` is the step to the best estimate; Basis (1.15), BU (0.75, since its switch: its active column was the best estimate and had no factor), FRV (0.75), Index (0.75, since its switch: its file was second order and had no factor), KLV (0.75), RLV (0.75, since its switch: its file was second order, read at the neutral factor, and a load made the first order), RV (1.15), Riester (0.75) and Sofort (1.2, since its switch: its file's second-order series was 1.20 of the first) override it from their `param_tariff_type.csv`; Pflege derives it, 1, since its tables stand at the best-estimate level and its loads make the first order (values package, open point 14 (a)).
- `mort_rate(t) = min(1, mort_rate_base(t) * mort_be_factor() * mort_be_trend(t))` (Basis, BU, FRV, Index, KLV, Pflege, RV), with `mort_be_trend(t) = 1`, the best-estimate trend term: only the best estimate may change a table's trend, and a product that does overrides the term. Sofort is the one that does, since its switch: its best estimate improves at `mort_be_trend_factor` 0.8 of its table's trend, `mort_be_trend(t, life) = ((1 - 0.8 tr) / (1 - tr)) ** (g + x - base_year)` on the table's `trend` and `base_year` cells, per life (section "The table factory", "The derivation"). IEEE `*` commutes, so FRV's former `factor * q` gave the same bits when it came to derive the cell (its `q` was the tariff rate of its unisex file then; since its switch to the table factory it is the table rate on the own sex, as in every switched product), `x * 1.0` is exact, so the neutral term moves no bit, and `min(1, q) == q` for `q <= 1`. Where `mort_rate_base(t)` is 1 the rate is 1 before any factor acts: a table rate of 1 is a certainty, the closing age of a table or its cap, and no best-estimate factor below 1 lets a survivor past it (section "The table factory", "The derivation").
- `mort_rate_mth(t)`, the geometric twelfth `1 - (1 - q)^(1/12)` of `q = mort_rate(t)`, so twelve months compound back to the annual rate. An annual rate of 1 is a certainty, not a rate: it is placed in the anniversary month, 1 where `is_anniv(t)` and 0 in the eleven months before, so the cohort is paid its last year and dies at its end (Basis, Index, RV, Riester; BU, KLV and RLV had the plain twelfth, and their rate stays below 1 on every baseline point, so the branch never acts there).
- `lapse_rate_base(t)`, the table annual lapse rate at `policy_year(t)`, holding the table's last row for later years (BU, FRV, KLV, Pflege, RV, Riester, RLV). `lapse_factor(t) = 1` is the factor on it, and `lapse_rate(t) = lapse_rate_base(t) * lapse_factor(t)`, 0 without reading the table where the factor is 0 (BU, Index, Pflege, Riester, RLV).
- `lapse_rate_mth(t)`, the same shape on `lapse_rate(t)`: an annual rate of 1, a dated contractual act such as the § 165 VVG cash-out, falls whole in the anniversary month (BU, Index, KLV, Pflege, RV, Riester, RLV).

The hooks into the table factory (section "The table factory"), each a core cell with the name a switched product reads or overrides; Index, BU, RV, KLV, FRV, Basis, Riester and Pflege, eight of the ten switched products, reach those that read the factory; RLV, the sixth, has no role `mort_table` and reads the factory in a hook of its own; Sofort, the ninth, reaches `mort_table_name()` and `omega_age_table()` and reads the rates in a hook of its own:

- `mort_table_name() = data.param("mort_table")`, the table of the tariff's main mortality role.
- `birth_year() = 0`, the year of birth a generational table is read at, none for a period table; a product whose model point carries a birth year overrides it (Sofort, one per life), and so does the reader of a generational table whose point carries the year and the age of issue: RV, the first, Basis and Riester, each with `issue_year() - issue_age()`, so that `birth_year() + age(t)` is `calendar_year(t)` and the table's rate is that of the policy year's calendar year. The neutral value is 0 and not `None`, since modelx refuses `None` as the value of a cell of a product's `Projection` (`_allow_none` is false in every product model, and a cell's own setting does not reach the cells of `Projection[point_id]`).
- `mort_rate_table(sex_code, x) = tables.q(mort_table_name(), sex_code, x, birth_year() or None)`, the one read of the factory in the core; no birth year reaches the factory as `None`, so a period table accepts the call and a generational one raises. Riester overrides it with `tables.q(mort_table_name(), sex_code, x)`: its main role is the period table `dav2008t_proxy` and its `birth_year()` is overridden for the generational table of its second role, which `q` would refuse on the first; the core's `mort_rate_at_age`, `mort_rate_base` and `mort_rate_mth` stand on the override unchanged.
- `mort_rate_at_age(x) = mort_rate_table(sex(), x)`, the base of the best estimate on the model point's own sex, and `mort_rate_tariff_at_age(x) = unisex_blend(mort_rate_table("M", x), mort_rate_table("F", x))`, the base of the tariff rate.
- `omega_age_table() = tables.end_age(mort_table_name())`, the limiting age read off the table. The core's `omega_age()` reads the item `omega_age`, which no file holds since the last switch, Pflege's, until the commit after it removes the old core cells; a switched product overrides `omega_age()` with `omega_age_table()` (a product with several roles with `tables.end_age` of its role's table), reason "reads the end age off its table". RV is the first to do so, Basis the second, Sofort the third, Pflege the fourth; Riester, with two roles, is the first to name its role, `tables.end_age(data.param("annuity_mort_table"))`, the end age of the lifelong phase's table; Index and BU read `omega_age()` on no path.

A product with several roles or a select table calls `tables.q` in a cell of its own. BU's is the first: `mort_rate_dis_at_age(sex_code, x)`, the rates of its second role, the lives in claim, by claim year, `tables.q(data.param("mort_dis_table"), sex_code, x, duration=year)` for each claim year of its claim-duration table, as a tuple; it names its choice item by a literal, so the usage scan sees the read. RLV's is the first whose table depends on the life: `mort_table_smoker(smoker_code)` maps the smoker status of a life to its role, `N` to `data.param("mort_nr_table")` and `R` to `data.param("mort_r_table")`, each by a literal, and raises on any other code, and `mort_rate_at_age(sex_code, smoker_code, x)`, its override of the core's cell of that name, is `tables.q(mort_table_smoker(smoker_code), sex_code, x)`, read for each of up to two lives. Riester's is the first whose second role is a generational table beside a period table of the first: `annuity_mort_rate(sex_code, x) = tables.q(data.param("annuity_mort_table"), sex_code, x, birth_year())`, the rate of the payout, by a literal as BU's. Sofort's is the first for two lives on one table: `mort_rate_gen(x, table_sex, cohort) = tables.q(mort_table_name(), table_sex, x, cohort)`, read for each life at its own birth year, the unisex `U` the core's `unisex_blend` of the two sexes, and 1 from the end age on without reading the table, a guard with its reason: on a joint-life point the frame runs to the younger life's horizon, so the older life's age passes 120 where `q` would raise (values package, open point 2). No core cell switches between the old and the new mortality: an unswitched product overrode the hook with its own table read, and its switch deleted the override.

The monthly split is a product choice, not a contract attribute, so a product that splits otherwise overrides the cell with its reason rather than setting a switch in its data (Moritz, 2026-10-26). The certainty branch reads `is_anniv(t)`, `t % 12 == 11`; BU's `t` counts from the valuation month, where that is not the anniversary, but BU's rates never reach 1.

The overrides, each with its reason in the cell's docstring:

- `mort_rate_at_age`: RLV, its hook on the factory, the table rate of a sex at the table of a life's smoker status; Index', BU's, RV's, KLV's, Basis', Riester's, Sofort's and Pflege's overrides went with their switches. `mort_rate_table`: Riester, its main role a period table read without the birth year of its second role. `mort_be_factor`: the nine products named above, each reading its item. `mort_be_trend`: Sofort, its best estimate improving at 0.8 of its table's trend, per life. `mort_rate_tariff_at_age`: none; KLV's and FRV's overrides went with their switches. `birth_year`: Sofort, one birth year per life from the model point; RV, Basis and Riester, the issue year less the issue age. `omega_age`: RV, Basis, Sofort and Pflege, the end age of their table; Riester, the end age of the table of its role `annuity_mort_table` (section "The time axis").
- `mort_rate_base`: RLV, the table on sex and smoker status, two lives combined to the first-death rate before loading, and 1 where the rate of either life is 1. FRV's override, `mort_rate_tariff(t)`, the unisex tariff file its flat factor stood on, went with its switch: its best estimate stands on the table rate of the own sex. Basis' override, the generational table of its own file at the attained age and the calendar year, went with its switch too: the core's cell gives the same on the factory's table at the birth year. Sofort inherits it unused.
- `mort_rate`: Riester, the basis switch at `t_conv()` from the period table of its main role to the generational annuitant table of its second role, read by its hook `annuity_mort_rate` on the own sex, and its own factor `annuity_mort_be_factor`, 1 where the table rate is 1, the rule of the core's cell held in the override (its guard forcing 1 from `omega_age() - 1` went with its switch); RLV, the *Risikozuschlag* and the selective-lapse loading beside the best-estimate factor, `min(1, mort_be_factor() * rating_factor() * mort_rate_base(t) * sel_lapse_factor(t))`, and 1 where the base rate is 1, the rule of the core's cell held in the override; Sofort, the argument `life` on its generational surface, its factor and its trend term on the own sex's rate of its hook `mort_rate_gen`, and 1 where the table rate is 1, the rule of the core's cell held in the override. Basis' override, the absorbing terminal age (1 from `omega_age() - 1` whatever the factor, where its file's generational trend carried the terminal rate below 1), went with its switch: the factory's table is 1 at its closing age for every cohort, and the core's cell passes it through.
- `mort_rate_mth`: FRV, the linear split `q / 12`, coupled to the *Risikobeitrag* struck on `q/12` times the *riskiertes Kapital*; Pflege, a published diagnostic of its force-based monthly step, the plain twelfth also at the limiting age; Sofort, the argument `life`.
- `lapse_rate_base`: Index, its table keyed on the 0-based policy year, read through `duration(t)`.
- `lapse_factor`: Index, 0 through the final policy year, which ends at *Rentenbeginn*; RLV, 0 through the final policy year, where cover expires, else `shock_lapse_factor(t)`; Pflege, 0 once the premium term has ended; Riester, 0 from `t_conv()`, a contract in payment cannot be surrendered.

Still in the products: the first-order and tariff rates (`mort_rate_tariff*`, Pflege's `tar_*`, BU's `*_first`), BU's disabled-lives and in-claim rates (`mort_rate_dis*`, read off the factory's select table since its switch), Pflege's forces and care rates (`mort_force`, `mort_force_care`, and `mort_rate_care`, the rate of the table of a care grade, read through its role cell `mort_table_grade` since its switch), Riester's payout basis (`annuity_mort_rate`, its hook on the factory since its switch) and transfer rate, Sofort's hook `mort_rate_gen` and its per-life rates, Basis's *Beitragsfreistellung* rate, and the surrender values and charges.

## The policy counts

The core's `Projection` holds the policy counts the monthly recursion is built from, on the rates above and the frame `t_start() .. proj_len()`:

- `pols_if_init()`, the policy count the model point stands for, from its `pols_if_init` column. The count is a contract-book attribute and so data: every product derives it, and RLV and BU, whose cell was the literal 1.0, carry the column, 1.0 on every shipped point.
- `pols_if(t)`, the count at the **start** of month `t` and the weight on that month's row: 0 outside `t_start() .. proj_len()`, `pols_if_init()` at `t_start()`, then `pols_if(t-1) - pols_death(t-1) - pols_lapse(t-1) - pols_maturity(t-1)`. Subtracting the exits makes `pols_if(proj_len()) = +0.0` exact where the survivors mature (RLV, Index).
- `pols_death(t) = pols_if(t) * mort_rate_mth(t)` (FRV, Index, KLV, RV, RLV), `pols_lapse(t) = pols_if_at(t, "AFT_DEATH") * lapse_rate_mth(t)` (FRV, Index, KLV, RV, RLV, Riester), the lapses taken from the survivors of the month's deaths, and `pols_maturity(t)`, 0 before the last month `proj_len() - 1` and the survivors of both decrements there, `pols_if_at(t, "AFT_DEATH") * (1 - lapse_rate_mth(t))` (KLV, FRV, Index, RLV); the lapse is closed in that month, so the factor is exactly 1.
- `pols_if_at(t, timing)` on one sequence of timings: `"BEF_DECR"`, the start of the month, `pols_if(t)`; `"AFT_DEATH"`, after the month's deaths, `pols_if(t) * (1 - mort_rate_mth(t))`; `"AFT_DECR"`, the end of the month after every exit, `pols_if(t + 1)`; any other timing raises `ValueError` (BU, Pflege, RLV, KLV, Riester). The products' labels for the same points were renamed to these: KLV `AFT_MORT` and `AFT_LAPSE`, RLV and RV `BEF_LAPSE`, BU and Pflege `BEG` and `END`. BU and Pflege read only `"BEF_DECR"` and `"AFT_DECR"`; the inherited `"AFT_DEATH"` is the single-decrement population, not the survivors of their ledgers, and nothing reads it there.

The float order carries the byte identity, as for the rates: a product derives a count only where the core expression gives its bits (`x - 0.0 == x`, `x * 1.0 == x`, `a - a == +0.0`). Index's and RV's `"AFT_DEATH"` subtracts the deaths, `pols_if(t) - pols_death(t)`, so they keep their `pols_if_at` and still derive `pols_lapse`, which reads it through their override. KLV's and Riester's `pols_if` read their own end-of-month expression, since the derived `"AFT_DECR"` is `pols_if(t + 1)`.

The overrides, each with its reason in the cell's docstring:

- `pols_death`: Basis, the deaths of the paying and the paid-up cohort summed; BU, the three ledgers' deaths summed; Pflege, every state at its own rate; Riester, zero outside the frame and in the conversion month of a commuted contract, where the *Kleinbetragsrenten-Abfindung* takes the whole cohort. Sofort has no such cell.
- `pols_if_at`: Basis, `"AFT_FREEZE"`, after the *Beitragsfreistellung* has moved policies between the cohorts; FRV, `"AFT_DECR"` is the cohort before the maturity sweep, not `pols_if(t + 1)`; Index, `"AFT_DEATH"` subtracts the deaths and `"AFT_LAPSE"` is the cohort before the maturity that `pols_surv_year_end` reads; RV, `"AFT_DEATH"` subtracts the deaths and `"AFT_DECR"` the commutation at *Rentenbeginn* too.
- `pols_lapse`: BU, from the *aktiv* ledger only; Pflege, from the active state's survivors and the month's reactivations.
- `pols_if`: Basis and Pflege, the sum of their ledgers; BU, death and lapse its only exits with no maturity, rolled forward so that `check_states` tests the ledgers against it; FRV and KLV, the multiplicative recursion `l(t) (1 - q^m) (1 - w^m)`, and KLV subtracts no maturity, so its `pols_if(proj_len())` is the maturing cohort its checks read; RV, the commutation exit; Riester, the transfer exit (*Anbieterwechsel*) and the *Abfindung*; Sofort, the probability that a payment obligation remains over two lives and the guarantee period, not a count.

Still in the products: the ledger counts (`pols_paying`, `pols_paidup`, `pols_actv`, `pols_dis`, `pols_act`, `pols_care`, `pols_pg`, `pols_karenz`, Sofort's `lives_if`), the exits other than death, lapse and maturity (RV's `pols_commutation`, Riester's `pols_transfer`, Basis's `pols_freeze`), `pols_tariff` of the tariff basis, the annuity counts (`pols_annuity`) and the surrender values.

Open work, each a result-changing commit of its own: FRV's and KLV's multiplicative `pols_if` and Basis's summed `pols_death` give other bits than the core form; Index's and RV's subtracted `"AFT_DEATH"` other bits than the core's product; KLV's `pols_if(proj_len())`, the maturing cohort, would become 0 with its checks rewritten on `pols_maturity`, and FRV's `"AFT_DECR"` at the last month would become `pols_if(proj_len()) = 0`.

## The cash flows

The core's `Projection` holds the monthly cash flows from the counts above, each a procedure of term cells with neutral defaults; a product overrides the terms that carry its own premium, benefit and cost amounts and derives the cell. The amounts themselves (the premium per policy, the death benefit, the surrender value, the annuity, the expense rates, `claim_expenses`, `annuity_payments`, `zulagen`, FRV's charges and `death_strain`) stay in the products, and a term override delegates to them or holds the expression the product's cell had.

- `premiums(t) = prem_inst_pp(t) * pols_prem(t)`, the premium collected per policy at the start of the month times the count it is collected from, with `prem_inst_pp(t) = 0` and `pols_prem(t) = pols_if(t)`. All ten derive it and override `prem_inst_pp`: KLV and RLV with their instalment, BU the *Zahlbeitrag* instalment `beitragsverrechnung() * prem_charged_inst_pp(t)`, Pflege `prem_charged_inst_pp(t)`, FRV `prem_charged_inst_pp(t) + topup_pp(t)`, Index and RV the year's premium where `prem_due(t)`, Basis the year's premium and *Zuzahlung* there, Riester the *Eigenbeitrag* and the extra contribution where due, Sofort `prem_gross_level_pp()` at `t = 0`. `pols_prem` is overridden by BU (*Beitragsbefreiung*: the *aktiv* ledger plus the disabled inside the *Karenzzeit*), Pflege (the waived lives taken out), Basis (`pols_paying(t)`) and Sofort (`pols_if_init()`, its `pols_if` being a probability). A month with nothing due gives `0 * pols = +0.0`.
- `claims(t, kind=None)`: the total `sum(claims(t, k) for k in claim_kinds())`, with `claim_kinds() = ("DEATH", "LAPSE", "MATURITY")`; `"DEATH"`, `"LAPSE"` and `"MATURITY"` are `benefit_death_pp(t) * pols_death(t)`, `benefit_lapse_pp(t) * pols_lapse(t)` and `benefit_maturity_pp(t) * pols_maturity(t)`, each benefit 0 by default; any other kind is `claims_other(t, kind)`, which raises `ValueError` in the core. Derived by RLV (`benefit_death_pp = benefit_paid_pp`; lapse and maturity exactly 0 from the neutral benefits), KLV (its death and maturity benefit, `surr_value_pp`, kinds `DEATH, MATURITY, LAPSE`), Index (`db_pp`, `cv_pp`, `mat_pp` at `duration(t)`), RV (`db_pp`, `cv_pp`, kinds `DEATH, LAPSE, COMMUTATION`, the *Kapitalabfindung* in `claims_other`), Riester (`db_pp`, `cv_pp` at `proj_year(t)`, its six kinds, transfer, lump sum, commutation and annuity in `claims_other`), BU (kinds `BU_RENTE, REINTEGRATION, LAPSE`, the first two in `claims_other`, the lapse 0) and Sofort (kinds `GUARANTEE, REFUND`, both in `claims_other`).
- `expenses(t) = expenses_acq(t) + expenses_maint(t) + expenses_claim(t)`, excluding commission, each term 0 by default. RLV, RV, Sofort and Riester override all three terms (Sofort's claim term is the payment run, Riester's maintenance term the accumulation maintenance plus the annuity expense); Basis overrides acquisition and maintenance, each with the frame guard, and derives the claim term 0; KLV and Index override `expenses_maint` with their per-policy rate, which carries the acquisition expense of the opening month, and KLV `expenses_claim = claim_expenses(t)`.
- `commissions(t) = comm_init(t) + comm_renew(t)`: `comm_init(t) = comm_init_rate() * beitragssumme() * pols_if(t)` in the frame's first month on new business (`duration_init() == 0`), else 0, and 0 without reading the *Beitragssumme* where `comm_init_rate() = 0`; `comm_renew(t) = 0`. KLV (the cost table's rate), Riester (`comm_acq_bsum_once`) and Basis (its charge table) override the rate and `comm_renew`; Riester's renewal is 0 in the month of the initial commission. RLV (`comm_init_pp()`) and FRV (`comm_acq_pp(t) * pols_if(t)`) override both terms. BU, Index, RV, Pflege and Sofort pay none and inherit exactly 0.
- `net_cf(t)`, income positive: `premiums(t) + income_other(t)`, less `claims(t, kind)` for each kind of `claim_kinds()` in turn, less `annuity_outgo(t)`, `expenses(t)` and `commissions(t)`, with `income_other(t) = annuity_outgo(t) = 0`. Derived by RLV, KLV, Index, RV (`annuity_outgo = annuity_payments(t)`), Basis and Riester (`income_other = zulagen(t)`). Basis overrides `claim_kinds` with `DEATH, ANNUITY, SURVIVOR` for it.
- `liability_cf(t) = -net_cf(t)`, the same stream outgo positive (all but Sofort).

The float order carries the byte identity: `x - 0.0 == x`, `0.0 + x == x` for `x != -0.0` and `a * b == b * a`, so a neutral term adds nothing and a product whose order the core formula keeps derives the cell. Subtracting the kinds one by one is the majority's order (KLV, Index, RV, Basis, Riester); RLV's `p - claims(t)` gives the same bits because its lapse and maturity claims are +0.0. Python's `sum` over floats is compensated (Python 3.12), so the core's claim total equals a product's `sum` over the same kinds, not a product's left-to-right `A + L + D`.

The overrides, each with its reason in the cell's docstring:

- `claims`: Basis, the death benefit releases the reserve of two cohorts weighted by the survivor's eligibility; FRV, the surrender value formed as count times fund times `(1 - sigma)`, another float order, and no total; Pflege, its total `A + L + D` added left to right.
- `expenses`: BU, the acquisition charge added to the proportional administration before the flat one, `(acq + prop) + flat`, which the core's `acq + (prop + flat)` would reassociate; FRV, five expenses added left to right (the per-event surrender and annuitisation expenses among them); Pflege, the *Zillmerung* allowance added after the two administration terms.
- `net_cf`: BU, the claim total at once and the *Leistungsbearbeitungskosten* after the expenses; Pflege, the claim total at once and the claims-handling cost; FRV, the non-unit cash flow, charges and *Stornoabzug* less expenses, commissions and the death strain; Sofort, `-liability_cf(t)`.
- `liability_cf`: Sofort, the notes' outgo-positive stream, annuity payments, claims and expenses less the premium.

A product inherits every term also where it has no use for it: Pflege and FRV inherit `claim_kinds` and the benefits unused, and the core's `claims(t, "DEATH")` on Sofort, which has no deaths of that form, is not evaluated. A kind outside a product's `claim_kinds()` but among the core's three (RV's `"MATURITY"`, Riester's `"MATURITY"`) gives the core's product of a neutral benefit and a count rather than a `ValueError`.

Still in the products: the per-policy amounts named above. The expense inflation the cost terms multiply follows in the next section, the result frames and `check_net_cf` after it.

Open work, each a result-changing commit of its own: Pflege's claim total in the compensated `sum`; FRV's lapse claim as amount times count and its five expenses, and Pflege's expenses, in the core's three terms; BU's expenses in the core's three terms; BU's, Pflege's and FRV's net cash flow from the core's terms (`claim_expenses` as an outgo term, FRV's charges as income); Sofort's `liability_cf` as `-net_cf`.

## The expense inflation

The core's `Projection` holds the expense inflation the cost terms of the cash flows multiply, as a rate and a factor built from one term:

- `expense_infl()`, the annual expense inflation rate, the item `expense_infl` of the core file, 0.02 for every tariff (RV's form); without the item `param` raises `KeyError`. RV had the cell and Pflege read the row inline; FRV (0.02), Riester (0.02), RLV (0.02) and Sofort (0.015) had a Reference and got the row, and Index's Reference `exp_infl` (0.015), the same rate under another name, became the row `expense_infl`. Entry 12 of epic-parameter-files aligned the seven rows to 0.02, the house-wide rate (Index, Pflege and Sofort each a result-changing commit), and moved the item to the core.
- `inflation_factor(t) = (1 + expense_infl()) ** inflation_years(t)`, with the term `inflation_years(t) = duration(t)`: the completed policy years, so the factor counts from issue and steps on the policy anniversary, flat across a policy year's twelve months. RLV, Sofort (its `infl_factor`, `t // 12` on the inception clock), RV, Riester, KLV and Index derive both; KLV's `expenses_pp` reads `inflation_factor(t)` where it read its own `inflation_factor(duration(t))`, and Index's year-indexed `exp_maint_pp(k)` reads `inflation_factor(12 k)`, `duration(12 k) == k` on its inception clock.

The overrides, each with its reason in the cell's docstring:

- `expense_infl`: none. KLV read a column `expense_infl` of `cost_table.csv` at `cost_id()`, 0.018, and Basis one of `charge_table.csv` at the tariff, 0.015, until Moritz's decision of 2026-11-10: the two columns and the two override cells are gone and both products derive the core's cell at 0.02, each in a result-changing commit of its own. Every product that inflates an expense now reads the one core item.
- `inflation_years`: FRV and Pflege, `t / 12`, inflation compounding continuously from inception (`1.02^(t/12)`, `(1 + f) ** (t / 12)`); Basis, `proj_year(t)`, the projection years from the valuation date, its `t` running on the valuation clock; its year-indexed `unit_cost_pp(k)` reads `inflation_factor(12 k)`, `proj_year(12 k) == k`.

The power is the same subexpression in the same place as in each product's own form, so every product's results are byte-identical. BU has no expense inflation (a German *Verwaltungskostenzuschlag* is fixed in the tariff, `products/berufsunfaehigkeit/technical-notes.md:360`) and inherits the three cells unused.

## The outputs and checks

The core's `Projection` holds the result frames and the cash-flow reconciliation, each a procedure of term cells: the core holds how a frame is built and checked, the product the columns it publishes and the scale it is checked on.

- `roll_fwd_tol()`, the tolerance the `check_*` identities close to, the item `check_tol` of the core file, 1e-8 for every tariff (RV's form; the row was named `roll_fwd_tol` until the acceptance of 2026-11-09); without the item `param` raises `KeyError`. Every product derives it. Until entry 12 of epic-parameter-files each product held the row in its tariff-type file, Basis, RV and Riester at 1e-9, BU, FRV, KLV, Pflege and RLV at 1e-10, Index and Sofort at 1e-8; entry 12 aligned them to 1e-8, with no result moving, and moved the item to the core. RV had the cell and Pflege read the row inline; the other eight had a Reference and got the row, BU, Index and RLV with their first `param_table.csv`. FRV's `val_tol` (1e-10), the same quantity with the same value, is merged into `check_tol`, which its checks read; RLV's `val_tol` (1e-9 beside its `check_tol` 1e-10) stayed a row of its own until entry 12 of epic-parameter-files aligned both to 1e-8, with no result moving, and is merged into `check_tol` too. `tests/test_check_tol_probe.py` disturbs one term of each product's roll-forward (`check_pols_roll_fwd`, Sofort's `check_lives_roll_fwd`) in memory by just above and just below the check's bound, and the check fails above and passes below.
- `result_cf()`, one column per `(label, cell)` pair of `result_cf_columns()`, each cell evaluated over `t_start() .. proj_len() - 1`, index named `t`. The default columns are the statement the core's cells make: `pols_if`, `premiums`, a `claims_<kind>` column per kind of `claim_kinds()` in its order, `expenses`, `commissions`, `net_cf`, `liability_cf`. KLV and RLV derive both. The other eight override `result_cf_columns` with their statement's columns in their order, a column that is not a cell of `t` alone (a claim kind) as a lambda of `t`, the frame's docstring moved to the term: Basis (the paying count, its three kinds), BU (three state counts, the paying count, the claims-handling cost, `liability_cf` before `net_cf`), FRV (the premium split into the unit fund, the charges, the *Stornoabzug*, the unit-fund outgo, the death strain), Index (no commission, `liability_cf` before `net_cf`), RV (the annuity count and payments, the *Kapitalabfindung*, no commission), Pflege (the state counts, the claims-handling cost, no commission), Riester (the paying annuity count, the *Zulagen*, six kinds) and Sofort (the annuity payments, two kinds, no commission).
- `result_cf_annual()`, RV's form: `result_cf` grouped by `policy_year = duration(t) + 1`, the flows summed and each column of `result_cf_counts()` (default `("pols_if",)`) taken at the year's start and placed first. Index, KLV, RLV and RV derive it; RV overrides the counts with `pols_if, pols_annuity`.
- `result_pols()` and `result_states()`, the monthly frame of `result_cf` over `result_pols_columns()` and `result_states_columns()`, both `()` by default. RLV and Sofort derive `result_pols` and override its columns (RLV's reserves through `res_pp_at` and Sofort's two lives as lambdas); Pflege derives `result_states` and overrides its columns (the grade ledgers and the sums over grades and *Karenz* months as lambdas).
- `result_cf_dict()`, `result_cf()` as plain dicts by column, `{label: {t: value}}`, in the frame's column order with the frame's values, built once per point; `check_net_cf_resid` reads it instead of a pandas row per month (epic-night-run, entry 6), and every product derives it.
- `check_net_cf_resid(t)`, the reconciliation KLV and RLV publish: on the frame's values at month `t`, read through `result_cf_dict()`, the columns of `net_cf_income_columns()` (default `premiums`) added left to right, less each column of `net_cf_outgo_columns()` in turn (default a `claims_<kind>` column per kind, then `expenses` and `commissions`), and the residual `net_cf` less that. KLV and RLV derive both terms; Riester overrides the income with `premiums, zulagen` (its kinds give the outgo); RV overrides the outgo with its three claims, `annuity_payments` and `expenses` and derives the income.
- `check_net_cf()`, every `abs(check_net_cf_resid(t))` within `check_net_cf_tol(t)` over `t_start() .. proj_len() - 1`, with `check_net_cf_tol(t) = roll_fwd_tol() * check_net_cf_scale(t)` and `check_net_cf_scale(t) = 1`. The scale overrides: BU `max(1, abs(bu_rente_pp(t)))`, Index `max(abs(premiums(t)), abs(claims(t)), abs(expenses(t)), 1)`, KLV `max(sum_assured(), 1)`, Pflege `max(pols_if_init() * max(rente_mth(), 1), 1)`, Riester `max(1, guar_pp(k_conv() + 1))`, Sofort `max(prem_gross_level_pp() * pols_if_init(), 1)`. FRV and RLV override the tolerance: FRV `check_tol * max(1, abs(net_cf(t)))`, RLV `check_tol * max(sum_assured(), 1)`. The two terms take `t`, so `tools/run_baseline.py` does not list them as checks.

The float order carries the byte identity as before: the core rebuilds the residual in the products' order (income first, then each outgo subtracted), a scale multiplies the tolerance where the product's own expression did, and `float(a) - float(b)` equals `float(a - b)` for RV. A frame's index is set by name (`frame.index.name = "t"`, a `Series` named `policy_year` as the annual grouper), since the grep test reads `Index` as a product prefix.

The overrides, each with its reason in the cell's docstring:

- `result_cf`, `result_states`, `check_net_cf`: BU, whose model point carries no `duration_init`, so the core's `t_start()` is not defined there; its frames run from the valuation month `t = 0` over its own column terms, its check over its tolerance term.
- `result_cf_annual`: Basis and Riester, indexed by the projection year `k` of the valuation clock and summed over each year's twelve-month slice.
- `result_pols`: Basis and RV, the annual state by projection or policy year.
- `check_net_cf_resid`: Basis (the rebuilt flow less `net_cf`, the reverse of the core's sign), BU (the premium leg from the *Zahlbeitrag* billed times the paying count), FRV (the first two charges as premiums less the premium to the unit fund), Index (the kind-less claim total), Pflege (from the cells of its claim kinds and the claims-handling cost), Sofort (the instalment through the single payment factor); each rebuilds by another route on purpose, its docstring naming the boundary it crosses.
- `check_net_cf`: Basis (one scale over the run, the largest `abs(net_cf)`), RV (also asserts `liability_cf(t) == -net_cf(t)`).

A product inherits every frame also where it has none: the core's `result_cf_annual`, `result_pols` and `result_states` are derived in products that do not publish them, and nothing evaluates them there.

Still in the products: the product frames of their own (`result_surplus`, `result_fund`, `result_index`, `result_acct`) and every check but `check_net_cf`, also those two or more products share (`check_pols_roll_fwd`, `check_av_roll_fwd`, `check_prem_split`, `check_decrement_closure`, `check_res_roll_fwd`, `check_equivalence`, `check_annuity_roll_fwd`, `check_conversion`, `check_states`). The runner lists every cell of a product's `Projection` whose name starts with `check_` and that takes no parameter, inherited ones included, so a core `check_pols_roll_fwd` would add a check to Sofort's pinned list, which has `check_lives_roll_fwd` instead; the pinned check lists must not change.

Open work: BU's frames and check derive once its time axis defines `t_start()` (its model point has no `duration_init`); Basis's and Riester's annual frames and `result_pols` of Basis and RV are annual-step views of their own, and the five residuals that cross another boundary stay by design.

## The core quota

The core quota of a product is the share of its executed formulas that come from the core (R8). An executed formula is a cell of the point's `Projection` ItemSpace that holds a value (`len(cell) > 0`) after `result_cf()` and every runner check (`run_baseline.check_names`) for every shipped point, the union over the points, with the model read by `mx.read_model` (the modelx engine, whose cells keep their values). An executed cell counts as core when the product's static `Projection` cell of that name is derived from the core base (`_is_derived()`); an override of a core cell and a product-only cell count as product. The cells of the table factory count too, and as core: a cell of the model's `CoreTables` that holds a value after the points ran is an executed formula, listed as `tables.<cell>`, a name no `Projection` cell can have. The space takes no `point_id` and is inherited by no product space, so its cells are read off the one `CoreTables` once every point has run, not off the point's ItemSpace. All ten execute them since their switches, the cells behind `q` and the law of their tables, `makeham` or, in Pflege, `gompertz_force`, RV, Basis, Riester and Sofort the trend cells too. `Data` cells, the loaders, are not counted. The quota counts distinct formulas, not calls: a cell evaluated in every month counts once.

The lower bound is 20 % for every product, and a product passes at quota >= 20 % (Moritz, 2026-10-28; epic-common-core Notes), with one exception: BU carries its own bound at its measured quota, 28 of 148 (Moritz, 2026-10-29, epic-night-run Notes, variant c, as recorded in `a5a4781`), since its cohort index, its *Leistungsdynamik* step and its per-claim-year rate arrays keyed by age are product cells of its `Projection`, inside the mutation domain. `LOWER_BOUND` and `PRODUCT_BOUNDS` in `tools/core_quota.py` hold them, `bound_for(product)` gives a product's bound, and `tests/test_core_quota.py` fails for any product below its bound.

## Contract data and charges

`model_point()` is the selected point's row as a dict by column, `model_point_table_dict()[point_id]`; a cell reads a column as `model_point()["<column>"]`. The row is shared with the table's dict cell and is read-only: a cell that assigned into it would change the point for every later read, so `model_point()` returns it as a `types.MappingProxyType` and such an assignment raises `TypeError`. FRV's `charge_row()`, its shared row of `charge_table.csv`, is read-only the same way, and BU's cached `cohort_year_idx(n)` and `cohort_anniv_step(n)` are arrays with `setflags(write=False)`. The core's `Projection` reads the model-point attributes at least two products share, each in the form they had: `policy_id`, `sum_assured`, `rating_factor` (the *Risikozuschlag*; what it multiplies stays the product's), `scenario_id`, `karenz_months`, `smoker` (checked against `smoker_codes()`, `N` and `S`; RLV overrides the codes with `N` and `R`) and `prem_term` (checked against `1 <= prem_term <= policy_term`). Naming equivalents were renamed with their model-point column (BU `risk_factor`, Basis `surplus_scenario_id`, RV `decl_scenario_id`, Riester `rentenbeginn_age`, FRV `annuity_age`, Index `ann_start_age`).

The premium payment frequency and its loading: `prem_freq()` reads the model point's `prem_freq`, checked against the keys of the product's `prem_freq_table()`, read from `prem_freq_file`, `prem_freq_table.csv` (KLV, Index, Riester, RLV, RV, BU, Basis, FRV, Pflege). The keys are `annual`, `half_yearly`, `quarterly` and `monthly` in every product, and every such table has the index column `prem_freq`, the column `instalments` (the instalments a year, 1, 2, 4 or 12, an `int`), the column `prem_freq_load` where the product charges a *Ratenzahlungszuschlag*, and `provenance` last. `prem_freq_load()` and `instalments()` read the columns of their names at `prem_freq()`, and `prem_cycle()`, the months between instalments, is `12 // instalments()` (BU, KLV, RLV, FRV, Pflege): the months of a year are the calendar, so no table holds the months. `prem_freq_load()` is 1 for a single premium (`prem_form() == "single"`) in every product, so Basis' override of that rule is gone; KLV (1 for an *echt* sub-annual payment) overrides it. Basis' four frequency factors, rows `prem_mode` of its `option_table.csv` until then, are its `prem_freq_table.csv`. FRV's and Pflege's tables have no `prem_freq_load`: FRV's stated instalment already carries any loading, and Pflege folds it into `load_admin_prem_inst`. The annuity payment frequency, the instalments of an annuity a year, is `ann_freq` in every product: Sofort's model-point column `ann_freq`, checked by its product cell `ann_freq()` against the keys of a table of its own (section "Formula literals"), and the row `ann_freq` of Basis' and Riester's tariff-type files.

The premium form: `prem_form()` reads the model point's `prem_form`, `regular` (*laufender Beitrag*) or `single` (*Einmalbeitrag*), and raises `ValueError` for another value (Basis, FRV, Index, RV, RLV, Pflege; Sofort's column is `single` on every point, and its own cells read neither it nor `prem_freq_load`). The values were `laufend` and `einmal` in FRV, RV and RLV, whose column RV and RLV named `premium_form`, and `level` for the regular premium in Index; Basis and RV read the column without a cell. A product whose model points have no `prem_form` column writes regular premiums only and reads `regular` (KLV, BU, Riester). A single premium carries no *Ratenzahlungszuschlag*, and every single-premium point carries `prem_freq = annual`, the one payment of its year (FRV's point 2 had `monthly`, read by no cell): RLV, whose single premium is the paying term 1 of the same equivalence, reads it as one instalment, the other products not at all. Pflege's *Einmalbeitrag*, the frequency `single` with the sentinel of 0 months until then, is `prem_form = single`. RLV overrides `prem_form` with its gate that `single` requires `prem_term = 1`. BU's `premium_form` (`dynamik` or `level`) and Riester's `contrib_form` are other quantities and keep their names.

The *Beitragssumme* and the acquisition charge on it: `beitragssumme() = beitragssumme_prem() * beitragssumme_years()`, the annual premium times the paying years (`prem_gross_level_pp()`, `prem_term()`; KLV). FRV and Pflege override the two terms for their premium form (instalments, a single premium counted once, Pflege's age-85 cap), Index only `beitragssumme_years` (`prem_term_y()`, a single premium counted once), its `prem_sum()` removed; Basis and RV (schedule sums with *Dynamik*) and Riester (a model-point column) override `beitragssumme`. `zillmer_amount() = zillmer_on() * alpha_rate() * beitragssumme()` with `zillmer_on() = 1`; KLV overrides `zillmer_on` from its model point, FRV's `alpha_rate` is the *Zuzahlungskosten* rate on a single premium (its `beitragssumme()` is then the premium once), and Riester spreads it over five years. BU's `beitragssumme_unit` (per euro of premium) stays.

The shared loaders in the core's `Data` beside the tables of entry 2: `surplus_table()` (Basis, Riester's `surplus_scenario.csv`), `charge_table()` (FRV; Basis, RV and KLV's `cost_table.csv` override its index term) and `hoechstrechnungszins_table()` (Sofort). KLV's and Index's `surplus_rate_table` and RV's `decl_rate_table` have other keys and stay.

### The premium amounts

A premium amount has one name per quantity in every product, model-point column and cell alike (Moritz, 2026-11-07 and 2026-11-10; entry 16 of epic-parameter-files). The name is built from four parts. `gross` means before the *Ratenzahlungszuschlag* φ, no `gross` means after φ. `level` is the amount at inception; an argument `(k)` or `(t)` is the amount of year k or month t, and the same quantity at another time keeps its stem. `inst` is an instalment, the amount of one month, where no `inst` is an annual amount. `pp` is per policy. All amounts are per policy:

| Quantity | Name |
|---|---|
| annual premium before φ at inception (the core's `beitragssumme_prem` reads it) | cell `prem_gross_level_pp()`, column `prem_gross_level_pp` |
| annual premium before φ of year k (*Dynamik*, term) | `prem_gross_pp(k)` |
| annual premium after φ of year k | `prem_pp(k)` |
| its instalment due in month t, before *Beitragsverrechnung* and *Zuzahlung* | `prem_charged_inst_pp(t)` |
| money collected per policy in month t: the *Zahlbeitrag* instalment plus any *Zuzahlung* (core; `premiums(t)` weights it) | `prem_inst_pp(t)` |
| annual / instalment *Beitragsverrechnung* | `prem_rebate_pp(k)` / `prem_rebate_inst_pp(t)` |
| annual *Zahlbeitrag* | `prem_paid_pp(k)` |
| premiums paid to date after φ (*Beitragsrückgewähr* base) | cell `prem_cum_pp(k)`, column and cell `prem_cum_pp_init` |
| premiums paid to date before φ (Index guarantee base) | cell `prem_gross_cum_pp(k)`, column and cell `prem_gross_cum_pp_init` |
| premium due in month t | `prem_due(t)` |

A product whose annual amounts are cells of a month takes `(t)` for `(k)` (RLV's `prem_pp(t)`, BU's `prem_gross_pp(t)`: the amount of the policy year month t falls in). A quantity only one product has keeps a name of its own beside the scheme, listed in the inventory below.

**`prem_due` is the only source of a zero for the end of the premium term**, in every product (Moritz, 2026-11-10). The paying term, *Rentenbeginn* and a single premium's one payment are conditions of `prem_due(t)`, and no premium cell tests them itself: a cell of the year grid reads `prem_due` at the first month of its year (`prem_due(12 * k)`; RLV's annual cells of a month at `12 * duration(t)`), a monthly cell at its month. The zero is written as an early `return 0.0`, never as a product with the predicate, since a product with a negative operand would give `-0.0`. So the contractual amount `prem_gross_pp(k)` carries no term (Basis, Index: nonzero also after the paying term), and every amount paid or charged is 0.0 where `prem_due` is false. A *Beitragsfreistellung* is no end of the term and stays in the cell that tested it (Basis' and Riester's contribution cells, KLV's `prem_pp`, RV's `prem_pp`, FRV's `prem_charged_inst_pp`). Each product's predicate:

| Product | `prem_due(t)` is true where |
|---|---|
| Basis | `t % 12 == 0` and the projection year `k = proj_year(t)` lies in the frame before *Rentenbeginn*, `0 <= k < k_conv()`; on a single premium only in year 0 and only where `duration_init == 0`; the *Zuzahlung* does not read it |
| BU | `duration_mth(t) % prem_cycle() == 0`; the premium is payable to the *Endalter*, where the frame ends, so there is no further condition (the *Beitragsbefreiung* is the count `pols_prem`) |
| FRV | on a single premium `t == t_start()`; else `t < 12 * prem_term_y()` and `(t - t_start()) % prem_cycle() == 0` |
| Index | `duration_mth(t) % 12 == 0` and the policy year `k = duration(t)` lies in the frame, `k_start() <= k < proj_len_y()`; on a single premium only `k == k_start()`, else `k < prem_term_y()` |
| KLV | `duration(t) < prem_term()` and `duration_mth(t) % prem_cycle() == 0` |
| RV | `duration_mth(t) % 12 == 0` and the policy year `k = duration(t)` lies before *Rentenbeginn* and inside the paying term, `0 <= k < aufschub_y` and `k < prem_term_y()`; on a single premium only `k == 0` |
| Pflege | `age(t) < prem_end_age()`; on a single premium `t == 0`, else `t % prem_cycle() == 0` |
| Riester | `t % 12 == 0` while the contract accumulates, `t < t_conv()` |
| RLV | `t >= 0`, `duration(t) < prem_term()` and `duration_mth(t) % prem_cycle() == 0` |
| Sofort | `t == 0`, the month of the *Einmalbeitrag* |

What is no premium term and keeps its own test: the phase of an account (Basis' `alpha_amort_pp` and `prem_to_av_pp`, whose *Zillmerung* instalments and *Stückkosten* outlive a single premium; RV's account charges; Riester's interest and benefit cells), the spread of an acquisition charge (Index, FRV), Basis' *Zuzahlung*, which is not bounded by the premium term (Moritz, 2026-11-10): `zuz_pp(k)` tests the *Aufschubphase* and `zuzahlung_end_dur` itself and `prem_inst_pp(t)` the first month of the projection year, as Riester's `zulagen(t)` does, so a single-premium point may pay a *Zuzahlung* after its one premium; the state's *Zulage*, which Riester's `zulagen(t)` pays in the first month of a year also in the conversion month, and the first-order tariff, where the paying term is a term of the equivalence (the core's `tariff_annuity` sums over `prem_term()`, RLV's and KLV's `res_pp_at` credit the net or *Zillmer* premium inside it). Pflege's `prem_cum_max_pp(t)` counts the instalments to date in closed form from `prem_end_age()` rather than through `prem_due`; both count the same months.

**The result column `premiums` holds the same quantity in every product, the money collected** (Moritz, 2026-11-10): `premiums(t) = prem_inst_pp(t) * pols_prem(t)`, the *Zahlbeitrag* including any *Zuzahlung*, with no gross or rebate column beside it. KLV, FRV, Index, RV, Pflege and Sofort publish that. Riester's `zulagen` stays a column of its own, since the state pays it, not the customer. BU publishes it since its result-changing commit: its `premiums` was the instalment before the *Beitragsverrechnung* with the rebate in a column beside it, and is the *Zahlbeitrag* now, the rebate the cell `prem_rebate_inst_pp(t)` that `check_prem_split` closes against the instalment due; `net_cf` and `liability_cf` moved by at most 3.0e-13 euro. RLV published the guaranteed instalments and the rebate in two columns beside `premiums` until its result-changing commit removed them, with the two cells behind them; its other columns are byte-identical and its statement is the core's default, so it derives `result_cf_columns`. So every product's `premiums` is the money collected.

## The parameter files

A scalar parameter, a rate, factor, amount or tolerance with one value per tariff, is a row of a parameter file and is read through one lookup in the core's `Data`, `param("<item>")`, always called with the item's name as a string literal, so that a scan of the code finds every item read (`data.param("<item>")` from a `Projection`). Four layers hold the items, each item in exactly one of them for a tariff:

- the core file `core/Core/Data/param_core.csv`, the technical and house-wide quantities with one value for every tariff type. It holds the technical items `rate_cap_eps` (1e-12): Pflege's nine guards cap a decrement probability at `1 - rate_cap_eps` before taking its force `-ln(1 - q)`, so that the force stays finite at the limiting age (section "Formula literals"); and `check_tol` (1e-8), the tolerance the `check_*` identities close to (section "The outputs and checks"). Since the acceptance of 2026-11-09 it also holds the statutory terms, whose statute gives one value for every tariff: the *Selbsttötung* window of § 161 Abs. 1 VVG `suicide_years` 3 (KLV, RLV), the spread of § 169 Abs. 3 VVG `surr_spread_years` 5 (Index, KLV, RV) and the run-off of § 174 Abs. 2 VVG `runoff_months` 3 (BU); the 12/62 rule of § 20 Abs. 1 Nr. 6 Satz 2 EStG, `tax_step_min_year` 13 and `tax_step_age` 62 (FRV); the *Höchstzillmersatz* of § 4 Abs. 1 DeckRV, `zillmer_cap_bsum` 0.025 (Index), the cap a tariff's acquisition loading or charge may not exceed, not that level; and Riester's *Zulagen*, *Sonderausgaben* and certification terms (EStG §§ 10a, 84 to 86, 89 and 90, kept for contracts concluded before 2027 by § 52 Abs. 50a EStG; AltZertG § 1 Abs. 1): `grundzulage` 175.0, `kinderzulage_pre2008` 185.0, `kinderzulage_post2008` 300.0, `berufseinsteiger_bonus` 200.0, `mindesteigenbeitrag_rate` 0.04, `foerder_ceiling` 2100.0, `sockelbeitrag` 60.0, `zulage_lag` 1, `guar_carve_out_cap` 0.2 and `teilkapital_cap` 0.3 and the *Kleinbetragsrente* threshold of § 93 Abs. 3 Satz 2 Nr. 1 EStG, `kleinbetrag_threshold_mth` 59.33, 1.5 % of the monthly *Bezugsgröße* 2026, aligned from 39.55 in entry 12. Beside them stand three Setzungen of the house, not of a tariff: the money-market rate `mmkt_return_ann` 0.015 (FRV), its capital-market view, the expense inflation `expense_infl` 0.02 (section "The expense inflation"), its wage and price development, and the valuation year `valuation_year` 2027, the valuation date 1 January 2027, which no cell reads: it is the date the model points are built against, and `tests/test_core.py` checks that every point of every product whose model points carry `issue_year` (`VALUATION_DATE_PRODUCTS`, read off the files: Basis, KLV, RV, Riester and Sofort) opens there, `issue_year` plus its completed policy years equal to it (Riester read it in its `issue_year()` override until its points carried the column). The quantity's nature decides, not the number of readers: an item one product reads is core where its value is house-wide;
- the table parameter file `core/Core/Data/param_tables.csv`, beside the core file: the numbers of the tables of the table factory, one value for every tariff that reads a table (section "The table factory"). It holds the eight items of `dav2008t_proxy`, the first table, entered with Index' switch, the fourteen of `dav1997ti_proxy`, entered with BU's, the fourteen of `dav2004r_proxy`, entered with RV's, and the eight each of `dav2008t_nr_proxy` and `dav2008t_r_proxy`, entered with RLV's; a file with the header alone would be a layer without items;
- the tariff-type file in the product folder, named by the product's Reference `param_file`: `param_tariff_type.csv` in all ten products, each renamed from the product's `param_table.csv` (RLV first, the other nine together);
- the tariff file `param_tariff.csv` in the product folder, optional: it appears only at the first value in which a tariff deviates from its tariff type, and the loader skips the layer where it is absent.

Every layer file has exactly the columns `item`, `value`, `basis` and `provenance`, in that order, and the loader checks the header. `provenance` says where the value comes from, in the vocabulary of the product's documents; `basis` says whether the value rests on a `source`, a statute, regulation, DAV table or library document that states it or a range of values containing it, or on a `Setzung`, the tariff's or the house's choice, also where a statute only caps or floors the value and the tariff sits at the bound (Moritz's acceptance of 2026-11-09); `provenance` then gives the statute or the library document and page (`bib <path> p. <n>`, umlauts written `ae`, `oe`, `ue` so that the files stay ASCII), or the reason for the choice. Every row has a `basis`; the last empty ones were the rows whose value entry 12 of epic-parameter-files changed, each filled in its value commit, and `tests/test_core.py` forbids an empty one. A value whose text, stripped, is digits only after an optional sign (`text.lstrip("+-").isdigit()`) is read as a Python `int`, `int(text)`; any other as a Python `float`, `float(text)`, so `1_000` and `1e3` are floats, not the `int` the first is as a Python literal. The one kind of item that holds no number is a table choice: an item whose name ends in `_table`, `<role>_table`, holds the name of a table and is read as a `str`. The loader checks the name's form only, lower-case ASCII letters, digits and underscores after a first letter (`[a-z][a-z0-9_]*`), and raises on a number or any other form; whether a table of that name exists is not the loader's to know. A name as the value of any other item is no number, as before. `float(text)` is correctly rounded, so a decimal literal moves from a Reference into a file byte-identically. There is no type column (Moritz, 2026-11-11): a value is typed by its notation, and a mutant of a value keeps the literal's notation, `3` an `int` and `3.0` a `float`.

Three cells, each built once per model, load the files: `param_paths()` builds the paths and names the file of each layer in turn, `{"core": param_core_path(), "tables": param_tables_path(), "tariff_type": input_dir() / param_file, "tariff": param_tariff_path()}`, the `"tariff"` entry only where its file exists; `param_rows()`, the only cell that reads them, reads each of those files once, as text (`dtype=str`, `keep_default_na=False`), checks its header and returns its data rows `{layer: [[item, value, basis, provenance], ...]}` in the order of the file; `param_layers()` types the values of `param_rows()` and returns the layers as `{"core": {...}, "tables": {...}, "tariff_type": {...}, "tariff": {...}}`, the `"tariff"` layer only where its file exists. `param_dict()` merges the layers in that order into one dict `{item: value}`; `param(item)` is `param_dict()[item]`, a dict lookup behind one cell, and an unknown item raises `KeyError` naming it. A missing core file raises on the first `param` call, a `ValueError` naming the file, as do a missing table parameter file and a missing tariff-type file; it is not silently skipped. The tariff file's path `param_tariff_path()` is a term cell, which a product may override like any core term; the core file's `param_core_path()` is not, since the core file is the one beside the core's loaders, and the usage scan reports a product that defines it; the table parameter file's `param_tables_path()` stands beside it, is no term either and is reported the same way.

The loader checks the files as it reads them, and a broken file raises `ValueError` on the first `param` call, naming the file or files and, for a row, the item: a file it cannot parse, a row wider than the header among them (the file is read without a header, so such a row cannot become an index); a header other than `item,value,basis,provenance`, naming the header found; an item that is empty or padded with whitespace, which is rejected, not stripped, since a padded item would be a key of its own and slip past the core lock; a value that is empty, no number (`abc`) or not finite (`nan`, `inf`); a table choice whose value is no name; an item standing twice in one file; an item of the core file or the table parameter file in a later file, naming both files (the core lock: a core item and a table's number have one value for every tariff, and a product does not override them; it covers a core item in the table parameter file too); an item standing in both the tariff-type and the tariff file (uniqueness: a later layer never silently replaces an item of an earlier one). `tests/test_core.py` breaks a scratch copy of RLV for each case, `tests/test_tables.py` for those of the tables layer and the table choices.

Whether every item is read and every call names an item is checked statically, by the usage scan `core/param_usage.py`, not in a run. `scan(model)` reads a product's modelx model, the formula sources of its `Projection` and `Data` cells only, evaluates no `Projection` cell (of the loader only `param_layers()`, `param_paths()` for the files' names, and `param_indirect()`; of the table factory only `items()`), and returns the layers, the items read with the cells reading them, the reachable cells, the declared indirect reads, the factory's tables with their items, the tariff's table choices and a list of problems. A call counts for a product only where its cell is reachable: the roots are the product's own cells (`_is_defined()`) in `Projection` and `Data` and every cell named `result_*` or `check_*`, the edges every `ast.Name` id and `ast.Attribute` attr in a cell's source that names a cell of either space. Counting every inherited core cell instead would flag the core's `omega_age`, `unisex_mix_male` and `expense_infl` in the products that inherit them unused. The edges are meant to over-approximate what a run evaluates; `tests/test_core_quota.py` checks that every `Projection` cell the core quota records as executed is reachable (`Data` cells are not compared). A cell that reads parameters other than by a literal `param("<item>")` declares them in the term `param_indirect()`, `{cell: (item, ...)}`, empty in the core; the declared items count as read by the cell. The table factory reads its items by a computed name and declares nothing there: the scan counts the items of the tables a tariff chooses as read (section "The table factory", "The usage check and the view"). The problems: a call or declared item naming an item no layer holds, an item of the tariff-type or the tariff file that no reachable cell reads, an undeclared indirect read, a declared cell that does not exist, a cell other than the loader cells (`param`, `param_dict`, `param_layers`, `param_rows`, `param_paths`) referencing the readers behind `param` or the files they read (`param_core_path`, `param_tables_path`, `param_tariff_path`, the Reference `param_file`), a product whose `Data` defines `param_core_path` or `param_tables_path`, a table choice naming a table the factory does not hold, a reachable cell reading an item of the tables layer itself, a table choice in the core or the table parameter file, an item of the tables layer that belongs to no table, and an item of a table in another layer than the tables layer. An item of the core file is checked across all ten products together, `unused_core_items(usages)`: it is used if any product reads it; `valuation_year`, which no cell reads, stands in `CORE_ITEMS_READ_BY_TESTS` of `tests/test_core.py` with the test that reads it. `tests/test_core.py` runs the scan on every product, which reports no problem, and on the core file, which has no unused item, and breaks a scratch copy of RLV for each problem but the table factory's, which `tests/test_tables.py` breaks on a scratch copy of Index with fixture tables. The parameter tool `tools/params.py <product>|--all` (entry 14 of epic-parameter-files) builds on the scan and reads the loader's cells, no file and no path of its own: it lists every item a tariff reads, the scan's `reads`, with its value and layer from `param_layers()` and the `basis` and `provenance` of its row in that layer of `param_rows()`. A chosen table's items are among the reads, in the layer `tables`, and no other table's. It writes every scan problem of a product on stderr, `<product>: <problem>`, and a product whose loader fails is not listed: its `ValueError` line stands on stderr and the tool goes on with the next product (entry 20). It exits 0 where no product has a problem or a loader error, 1 where one has, and 2 on a usage error, among them a product named twice, by the same name or by two names of one folder. `tests/test_params.py` checks it against the scan and the loader and breaks a scratch copy of RLV for each case, a scratch copy of Index with fixture tables for those of the table factory.

The core file lives beside the core's loaders rather than at `core/param_core.csv`, and `param_core_path()` finds it as `_model.path / "CoreData" / "param_core.csv"`, through the product's `CoreData` symlink: `param_file` resolves against `input_dir()`, the product folder, and a scratch copy of a product folder (tests, `tools/measure_marginal.py`) copies the `CoreData` folder through the symlink and with it the core file, so a copy reads its own core file and a test can give it a fixture item without touching the core (Moritz, 2026-11-04). `param_tables_path()` finds the table parameter file the same way, `_model.path / "CoreData" / "param_tables.csv"`, so a copy has its own and a test can give it a fixture table. `mx.read_model` ignores a CSV file in a space folder, and `tests/test_provenance.py` does not descend into the symlinked folder, so the file adds no cell and no product file.

Every parameter read goes through `param`: the core's parameter cells `omega_age`, `unisex_mix_male`, `expense_infl`, `roll_fwd_tol` and `mort_table_name` and the products' own reads (RV, Pflege, Basis, FRV, KLV, Riester) call `data.param("<item>")` and take its value as `param` types it, `int` for a digits-only text and `float` otherwise; a cast stays only where it converts, `float()` on the two counts Pflege's `recov_age_ref` (75) and FRV's `glide_months` (60). The former DataFrame and dict readers `param_table()` and `param_table_dict()` had no reader left and are gone; `tests/test_core.py` fails on a source that still names them.

### Parameter names

The same quantity has the same item name in every product (Moritz, 2026-11-07). A cost parameter, the amount or rate of a cost, charge, loading or commission, is named `<category>_<kind>_<base>_<period>`:

- **Category**, decided by what the code does with the item: `expense`, a cost of the company, a second-order cash flow; `comm`, a commission; `charge`, deducted from the customer's contract or account (unit-linked, Riester, Index); `load`, a loading of the first-order tariff or premium calculation (alpha, beta, gamma, *Zillmersatz*). An item that prices the premium and is also charged as a cash flow is a `load`.
- **Kind**: `acq` (*Abschluss*), `admin` (*laufende Verwaltung* in the accumulation or active phase; `admin_pup` where the premium-free phase has a rate of its own, as RV's, refined like `claim_assess`), `annuity` (*Verwaltung* in payout), `claim` (*Leistungsfall*; `claim_assess` and `claim_admin` where split), `surr` (surrender), `conv` (*Verrentung*), `pay` (payment run), `collect` (*Inkasso*), `transfer` (*Anbieterwechsel*), and for commissions `acq` and `renew`.
- **Base**: `pp`, euro per policy or per event, or the base of a rate: `bsum` (*Beitragssumme*), `prem` (gross premium or contribution), `sp` (single premium), `av` (account or fund value), `sum` (sum insured or benefit), `annval` (annuity present value).
- **Period**: `once` (at issue or per event), `ann` (a year), `mth` (a month), `inst` (per premium instalment or per payment).

A rate is a fraction in every file: Pflege's acquisition rate, 25 per mille as `acq_permille`, is `load_acq_bsum_once` 0.025, and its formulas lost the `/ 1000.0`. Other shared quantities: a first-order load on a decrement is a factor named `<decrement>_load_first`, as BU's; the unisex male share is `unisex_mix_male`, read through the core's `unisex_mix_male()` where a product blends; the years over which the acquisition charge is spread are `acq_spread_years`, another quantity than the § 169 Abs. 3 VVG floor `surr_spread_years`; the share of the *Bewertungsreserven* is `bwr_rate`; the *Stornoabzug* rate is `stornoabzug_rate`; the base year of a generational mortality table is `mort_base_year`. `expense_infl` is an inflation rate, not a cost, and keeps its name. The tolerance of the `check_*` identities is `check_tol` in every product, also where a check is no roll-forward; the core cell that reads it keeps the name `roll_fwd_tol()`, since a cell named `check_*` without a parameter would be a check the runner lists and pins. A cell whose name only repeated an old item name took the new name (RV's four expense cells, Pflege's five margin cells and its two recovery-shape cells), and so did a cell that only repeated an old column name (FRV's five charge cells, KLV's `load_admin_prem_inst`, `load_admin_sum_ann` and `stornoabzug_rate(k)`); a core hook cell (`alpha_rate()`, `comm_init_rate()`) and an amount that is not the column (Basis' `unit_cost_pp(k)`, the inflating *Stückkosten*) keep their names.

## The table factory

The table factory is the one place the mortality rates of the ten products come from, through one cell, `q`: a tariff chooses a table by name and sets its factors on it, and no product ships a mortality table or holds a mortality formula. What is built is the scaffold (epic-table-factory, entries 1 and 2), the space, its parameter layer, the name-valued table choices, the lookup, the core's hooks and the usage check of the table parameters, and all ten switches (entries 5 to 14): the factory holds eleven tables, `dav2008t_proxy`, the select table `dav1997ti_proxy`, the generational table `dav2004r_proxy`, the two smoker tables `dav2008t_nr_proxy` and `dav2008t_r_proxy`, and Pflege's six on the law `gompertz_force`, `pflege_aktive_proxy` and one per care grade, `pflege_pg1_proxy` to `pflege_pg5_proxy`; Index reads its death rates from the first, BU those of its active lives from the first and those of its lives in claim from the second, RV its own from the third at the birth year, KLV its own from the first, which is its former file's law, FRV the rate of its *Risikobeitrag* and its best estimate from the first, RLV its own from the two smoker tables, by the smoker status of each life, Basis its best estimate from the third at the birth year, Riester the deaths of its accumulation from the first and those of its payout from the third at the birth year, Sofort its tariff rate and its best estimate from the third at the birth year of each of two lives, Pflege those of its active lives from `pflege_aktive_proxy` and those of its lives in care from the table of their grade, and none of the ten ships a mortality file. Every table of the factory has a reader. A table entered with the switch of its first reader, and each product switched in a result-changing commit of its own.

The tables, their items and every tariff's choices and derivation values come from one values package, accepted by Moritz on 2026-11-18 before the first switch (AD-4 of the epic's architecture). A switch enters its rows verbatim, value, basis and provenance; it adds no item the package does not list, and a table's values do not change after its first reader has switched.

The tables are proxies. The DAV tables they stand in for are the DAV's property and are not redistributed; a proxy is a law with a few parameters, chosen to be roughly realistic, each parameter with a source or marked as a Setzung.

### The factory's space

The factory is the third space of the core, `core/Core/Tables`. It enters each product model as the symlink `CoreTables`, beside `CoreData` and `CoreProjection`, and is listed in the model's `_spaces` (section "How a product reaches the core").

No product space inherits it, unlike the other two core spaces. A product's `Projection` reads it through the Reference `tables`; the factory reads the parameter loader through its Reference `data`. A product therefore cannot override a cell of the factory: a table is the same for every product that reads it. `tests/test_tables.py` checks in every product that `CoreTables` is that symlink, is a base of no space and holds the core's cells and no other.

The factory holds no contract data. The space takes no parameter, so there is one `CoreTables` per model and no `CoreTables[point_id]`, and its cells read only `data.param(...)`, each other and `math.exp`; a test walks the source for any other name. `math` is the space's one Module Reference beside `data`, admitted for the exponential function of the law `gompertz_force` (AD-2, amended on 2026-11-18; values package, open point 18); the module holds no contract data, and a read of any other module or of another function of it is reported. What depends on the contract reaches the factory as an argument of `q`. The runner's per-contract cleanup deletes the point's `Projection` item and leaves the space alone, so a rate is computed once per run and worker and looked up afterwards; the test runs a scratch copy through the export engine and finds the first point's rates still held after every later point.

- `gompertz_force(table, sex, x)`: `1 - exp(-b * c ** x)`, the law of Gompertz on the force, with the parameters `<m or f>_b` and `<m or f>_c` of the sex: the force of mortality `b * c ** x` held constant over the year of age. It is the one cell of the space that reads beyond `data.param` and its own cells, `math.exp`. On the force a multiple of a table's mortality is a multiple of its `b`, so a care grade is a table and no factor (AD-4, AD-6): `pflege_aktive_proxy` is Pflege's former file, `b` 1.47884e-05 and `c` 1.11068 for a man, 4.7629e-06 and 1.119962 for a woman, anchored at `q(65)` 1.35 % and `q(85)` 10.5 % for a man and 0.75 % and 7.0 % for a woman, and `pflege_pg<g>_proxy` is it with `b` times the grade's multiple, 1.5, 2.5, 3.5, 6.0 and 9.0, the former column `mort_mult` of `care_table.csv`, exact to the items' digits; the slope `c` is the active table's. The law reaches 1 at no age the tables hold; the rate is 1 at the closing age 109, lower than the 121 of the DAV proxies, a Setzung of the grid. The six tables stand at the best-estimate level (values package, open point 14 (a)), as `dav1997ti_proxy`: Pflege's loads make the first order.
- `trend_linear(table, sex, x)`: the annual improvement rate, the same for both sexes and piecewise linear in the age, `trend_start` up to `trend_start_age`, linear to `trend_mid` at `trend_mid_age`, linear to 0 at `trend_end_age` and 0 beyond; on `dav2004r_proxy` 0.025 up to 75, 0.0125 at 90 and 0 from 120. It reads its five numbers through `parameter(table, name)` like a law.

The other cells: `definition(table)`, the entry of one table, a `ValueError` for an unknown name; `items()`, `{table: (item, ...)}`, the items of each table, which the usage scan reads; `parameter(table, name)`, `data.param(table + "_" + name)`, the factory's one read by a computed name; `first_age(table)`, `end_age(table)` and `base_year(table)`; `select_factors(table)`, the values of `sel_1`, `sel_2`, … in that order; `base_rate(table, sex, x)` and `trend(table, sex, x)` (below); the laws, `makeham` and `gompertz_force`, and the trend law, `trend_linear`; and `q`.

Below `q` the machinery does not say mortality: a law is a function of its parameters and a key, and no cell name but `q` contains `mort` or `q` (a test checks it), so the other decrements can join later. The source holds no numeric literal but 0 and 1, which a test checks too: a table's numbers are rows of its parameter file. Its one Module Reference, `math`, gives the exponential function and nothing else.

### The lookup

One cell hands out rates:

```python
tables.q(table, sex, x, birth_year=None, duration=None)
```

- `table` is the table's name, `sex` is `M` or `F`, `x` the attained age.
- `birth_year` is required for a generational table and refused for a period table. The rate at age `x` is that of the calendar year `birth_year + x`: the base rate times `(1 - trend) ** (birth_year + x - base_year)`.
- `duration` is required for a select table and refused for a table without selection. It is the year since the claim began, counted from 1; the rate is multiplied by `sel_<duration>`, and past the last select year the last factor holds.
- The rate is capped at 1. At the table's last age, `end_age - 1`, it is exactly 1, whatever the trend and the selection: the closure is the table's.
- Rates are computed in double precision and are not rounded.

Where a call does not fit the table, `q` raises a `ValueError` naming the table and the argument: an unknown table, a `sex` other than `M` and `F`, an age outside `first_age .. end_age - 1`, a missing or a refused `birth_year` or `duration`, a `duration` below 1. It never clamps an age; a product that needs a guard keeps it in a cell of its own, with its reason. A table that names a parameter the tables layer does not hold raises the loader's `KeyError`. Every shipped product holds the same factory, also one no cell of which reads a table: `q("dav2008t_proxy", "M", 40)` is the same rate in all ten, and any other name raises.

Beside `q` stand the two cells a best-estimate trend term needs: `base_rate(table, sex, x)`, the law's own rate after the checks of table, sex and age, neither capped nor closed, and `trend(table, sex, x)`, the trend law's annual improvement rate, a `ValueError` on a period table. Sofort's trend term, the first, reads `trend` and `base_year(table)`. `q` takes no derivation argument.

### The derivation

What a tariff makes of a table rate stays in `Projection`, in the core's term cells, which a product overrides where it differs. Two factors stand on the table rate, each on its own, never one on the other:

```text
tariff rate   = unisex_blend(q(table, M), q(table, F)) × <rate>_load_first
best estimate = q(table, own sex) × mort_be_factor × mort_be_trend
```

The trend term is 1 but in Sofort, the one reader whose best estimate improves otherwise than its table: `mort_be_trend = ((1 - k × trend(x)) / (1 - trend(x))) ** (birth_year + x - base_year)`, read off the factory's `trend` and `base_year` cells with `k` = `mort_be_trend_factor`, so that on the table rate `base × (1 - trend) ** n` the best estimate improves at `k` of the table's trend, `base × (1 - k × trend) ** n` below the cap.

A table rate of 1 passes through both as 1. `q` is 1 at a table's closing age, its end age minus one, and wherever its law reaches 1 and the cap binds; behind `q` the two cannot be told apart and are treated alike. So `mort_rate(t)` returns 1 where `mort_rate_base(t)` is 1, whatever `mort_be_factor()` and `mort_be_trend(t)`, and `mort_rate_tariff(t)` returns 1 where `mort_rate_tariff_base(t)`, the unisex blend, is 1, whatever `mort_load_tariff(t)`: a factor below 1 or a load keeps no survivor past the closing age, and the guards with which a product forces a rate of 1 today go with its switch. The rule entered the core in one commit before the first switch that changed no result: of the products that derived the two cells then, only KLV read a file rate of 1 through `mort_rate` with a factor below 1, from age 110, which no shipped point reaches; since its switch it reads the table's, 1 at the same ages. `tests/test_tables.py` shows it on a scratch copy of Index whose fixture table closes at the last age a point attains, with a factor of 0.75, a trend term of 0.5 and a load of 1.25.

The hooks that read the factory are core cells with fixed names, listed in section "The decrement rates": `mort_table_name()`, `birth_year()`, `mort_rate_table(sex_code, x)`, `mort_rate_at_age(x)`, `mort_rate_tariff_at_age(x)`, `omega_age_table()` and the neutral trend term `mort_be_trend(t)`. A switch adds none. ### The usage check and the view

The usage scan `core/param_usage.py` (section "The parameter files") evaluates the factory's `items()`, the one cell of the factory it evaluates, and no rate. A product reads the items of exactly the tables its `<role>_table` items name: every item of a chosen table counts as read by the cells that read the choice item, for `mort_table` the core's `mort_table_name()`, for BU's `mort_dis_table` its own `mort_rate_dis_at_age`, for RLV's `mort_nr_table` and `mort_r_table` its own `mort_table_smoker`, for Riester's `annuity_mort_table` its payout hook `annuity_mort_rate` and its `omega_age`, which names the role, for Pflege's `mort_pg1_table` to `mort_pg5_table` its role cell `mort_table_grade`. An item of a table the tariff does not choose is not read by it, and a choice item no reachable cell reads is reported as any unread item of a product file, its table's items not counted. The scan's `Usage` holds both sides, `tables`, `{table: (item, ...)}`, and `choices`, `{choice item: table name}`.

Six things can be wrong, and the scan reports each:

- a chosen name the factory does not hold, a problem of the product, naming the choice item, its file and the name;
- an item of the tables layer that `items()` lists for no table, a problem of the product too, naming the item and the file. Every product loads the same table parameter file, so such a row shows in all ten, as a broken core file does;
- a reachable cell of `Projection` or `Data` that reads an item of the tables layer itself, by a literal `param("<item>")` or a `param_indirect()` declaration: a table's items are read through the factory, by the tariffs that choose the table. The problem names the cell and the item;
- an item `items()` lists for a table that stands in another layer than `tables`, the core, the tariff-type or the tariff file, where `param` would find it: a table's numbers are rows of the table parameter file alone. The problem names the item, the table and the file;
- an item named `<role>_table` in the core file or the table parameter file: a table choice stands in the tariff-type or the tariff file, and one elsewhere is no choice for the scan and the view though a run would read it. The problem names the item and the file;
- a table no tariff chooses. One product cannot tell, so it is checked across all ten together, `unchosen_tables(usages)`, as `unused_core_items(usages)` checks the core file: a table is chosen if any product has a choice item that names it and that a reachable cell reads.

An item a chosen table names that the tables layer does not hold is the scan's existing problem, an item read that stands in no layer. `tests/test_tables.py` runs the scan on every product, which reports nothing: each holds the factory's eleven tables, Index, KLV, RV, FRV, Basis and Sofort their choice and the table's items as read through `mort_table_name()`, BU its two choices, the items of the second as read through `mort_rate_dis_at_age`, RLV its two, the items of both as read through `mort_table_smoker`, Riester its two, the items of the second as read through `annuity_mort_rate` and `omega_age`, Pflege its six, the items of the active table as read through `mort_table_name()` and those of the five care grades' through `mort_table_grade`, and no table is unchosen across the ten: without BU `dav1997ti_proxy` would be, without RV, Basis, Riester and Sofort `dav2004r_proxy`, without RLV the two smoker tables, without Pflege its six. It breaks a scratch copy of Index with the fixture tables for each case; where a case needs a product without a choice, the copy loses its row `mort_table` and gets a `mort_rate_at_age` of its own, as a product before its switch.

The view follows from the scan. `tools/params.py <product>` lists the scan's reads and keeps no item list of its own, so it shows, beside the tariff's other parameters, the items of its chosen tables and no others: in the layer `tables`, after the core items and before the tariff-type items, each with its value, basis and provenance, and the choice item itself in the layer of the file it stands in, `tariff_type` or, where the tariff deviates in `param_tariff.csv`, `tariff`. A tariff that chooses no table shows no item of the layer: `tools/params.py indexpolice` lists `mort_table` and the eight items of `dav2008t_proxy`, `tools/params.py berufsunfaehigkeit` its two choices and the items of both tables, eight and fourteen, `tools/params.py klassische_rentenversicherung` `mort_table` and the fourteen items of `dav2004r_proxy`, its base year and end age among them, and neither `mort_base_year` nor `omega_age`, `tools/params.py kapitallebensversicherung` `mort_table` and the eight items of `dav2008t_proxy`, `tools/params.py fondsgebundene_rentenversicherung` `mort_table`, `unisex_mix_male`, `mort_be_factor` and the eight items of `dav2008t_proxy`, `tools/params.py risikolebensversicherung` its two choices, `mort_be_factor` and the sixteen items of its two tables, and no `mort_load_first`, `tools/params.py basisrente` `mort_table`, `mort_be_factor` and the fourteen items of `dav2004r_proxy`, and neither `mort_base_year` nor `unisex_mix_male`, `tools/params.py riester_rente` its two choices, `mort_be_factor`, `annuity_mort_be_factor`, `unisex_mix_male` and the items of both tables, eight and fourteen, and no `mort_base_year`, `tools/params.py sofortrente` `mort_table`, `mort_be_factor`, `mort_be_trend_factor`, `unisex_mix_male` and the fourteen items of `dav2004r_proxy`, and neither `mort_base_year` nor `omega_age`, `tools/params.py pflegerentenversicherung` its six choices, `mort_actv_load_first`, `mort_care_load_first`, `unisex_mix_male` and the 36 items of its six tables, and no `omega_age`. ## Formula literals

Every numeric literal in a formula cell of the core's `Projection` and the ten products' `Projection` spaces was reviewed (epic-parameter-files, entry 8, and its follow-ups of 2026-11-06): the cells "The new M" counts in `docs/roadmap.md` (module-level `def`s and non-underscore `name = lambda`, walked whole), with the literals inside a subscript and in the arguments of `range(...)` included and the values 0, 1, 0.0 and 1.0 excluded; docstrings hold no formula. The `Data` spaces and the products' `__init__.py` hold no such literal. A literal is actuarial when it states an assumption or a statutory term a tariff could set otherwise; then a parameter mutant on it was a code change, and it became a row of a parameter file. Further rules decide the rest (Moritz, 2026-11-06):

- **Basic arithmetic units are code.** Per mille (÷ 1000) and percent (÷ 100) are arithmetic every reader knows, not a convention a tariff sets, so they stay literals in the formula wherever a value is quoted in them. A parameter file quotes every rate as a fraction, so Pflege's acquisition rate is `load_acq_bsum_once` 0.025, as BU's and RLV's (it was `acq_permille` 25 with `/ 1000.0` in three formulas; section "Parameter names"), and no per-mille literal is left.
- **Solver settings are code.** The iteration count, the search bracket and the convergence tolerance of a numerical solve decide how it finds the answer, not what the tariff is, so they stay literals in the formula: FRV's bisection of `irr_ann` on `[-0.99, 5.0]` in `range(200)` and Sofort's of the refund solve in `annuity_pp_derived`, `range(200)` to `hi - lo <= 1e-10`. They are written in the formula, not as References, since no numeric Reference but `point_id` is left on a `Projection` (`test_no_numeric_projection_reference_remains`).
- **A table's length is read from the table, never written as a literal.** A cap at a table's last row, its last index or its row count is a `Data` cell computed once per model from the table's index, which the formula reads in the literal's place.
- **Payment frequencies are parameters, not code.** A set of allowed frequencies, or a map from a frequency to its months or instalments, is a table of the product's own: a CSV with a `provenance` column, its Reference and reader in `Data`, and a dict or keys cell built once per model that the cell checks the model point against, as the core's `prem_freq_table` and `prem_freq_table_dict` serve `prem_freq`. A single frequency, such as an annual annuity paid in twelve instalments, is a row of the tariff-type file.
- **The *Rentenfaktor* unit is a parameter.** The *Rentenfaktor* is quoted per 10,000 of capital, a market convention a tariff could quote otherwise, so `rf_unit` is a row of the tariff-type file, with one item name and one type in every product.

What stays code: the calendar (months per year, the last month of a policy year, the months of a year), basic arithmetic units, solver settings and bisection midpoints, and structure indices.

## Pull requests

Rules for a story built as a stack of pull requests, learnt in epic-parameter-files (retrospective A9: PRs #43 to #49 were merged into the branch of their base PR #42 after #42 was in `main`, and only the collecting PR #51 brought them there):

- **A stacked PR is retargeted before its base is merged.** Before a base PR is merged, its followers are retargeted to `main` (`gh pr edit <n> --base main`), or the stack is merged bottom-up, each follower retargeted to `main` once the PR below it is in. A PR merged into its base's branch after that branch is merged lands on a dead branch, not on `main`.
- **After a rebase, `baseline_revision` follows.** Once a plan's commits reach `main` rewritten (by a rebase or a squash), its `baseline_revision` moves to the rewritten commit there, not left at the SHA of the old branch, which other clones do not have.

## Commit trailers

Every commit that touches the core or a product model follows these rules from the first phase-3 commit on. Trailers stand in the last paragraph of the commit message, before `Co-Authored-By`.

- **Byte-identical commit** (refactor, unification without result change, reasoned override, tests, docs): no result trailer. A commit without `Result-Change` claims that every product's results are byte-identical to the commit before; the `pytest` gate (`tests/test_baseline.py` with its pinned hashes) proves it. A value commit that changes no baseline (a check tolerance aligned) carries `Reason` and `Checked-By` as below but no `Result-Change`, which the tool would report as `NO CHANGE`, and its body says "Results are byte-identical."
- **Result-changing commit**: one trailer naming every product whose results change, the reason, and the agent check:

  ```text
  Result-Change: risikolebensversicherung, kapitallebensversicherung
  Reason: products/kapitallebensversicherung/technical-notes.md, section …
  Checked-By: <agent>: <verdict>
  ```

  `Reason` points to the document and place that justify the change (product docs, a decision); `Checked-By` names the agent that checked the change and its verdict. The same commit updates the affected baselines and their pins. Every deviation from the tag `phase-2-baseline` leads to exactly one such commit.

  The listing of every deviation:

  ```bash
  uv run python tools/baseline_deviations.py
  uv run python tools/baseline_deviations.py --json /tmp/deviations.json
  ```

  The tool reads git only. A deviation is a commit in `phase-2-baseline..HEAD` that changes the content of a product's `baseline/<product>/result_cf.csv` (a mode-only change does not count), adding or removing it included: two commits that change one product's baseline are two deviations, and a change reverted later is still one. A merge counts only for content no parent brings (an evil merge); a PR's change is listed at its branch commit. The tool lists every marked deviation (product, commit, subject, `Reason`), prints `no baseline deviation from phase-2-baseline (<sha>)` when there is none, and exits 1 with each problem on stderr: a deviation whose `Result-Change` does not name the product (`UNMARKED`), a `Result-Change` without a non-empty `Reason` or `Checked-By` (`INCOMPLETE`), a `Result-Change` naming a product whose baseline that commit does not change (`NO CHANGE`), a `Performance: within-rounding` commit that changes a value of a product beyond the tolerance or whose baselines are not comparable (`OUT OF TOLERANCE`, naming the worst breach). It reads the trailers from the trailing paragraphs of the message that consist only of `Key: value` lines, the result trailers' paragraph before the `Co-Authored-By` paragraph included. A missing tag exits 2; fetch it with `git fetch --tags`. A failing git call also exits 2, with `error:` and git's message on stderr. `tests/test_baseline_deviations.py` runs the tool on the repository, so `pytest` fails on an unmarked deviation, and checks every case on a throwaway repository.
- **Performance commit** (epic-night-run), in one of two forms:
  - `Performance: byte-identical`. Results stay byte-identical; the trailer marks the commit as a speed-up rather than a refactor.
  - `Performance: within-rounding`. The commit changes results within rounding and is also a result-changing commit: it rewrites the affected baselines and their pins and carries `Result-Change`, `Reason` and `Checked-By`, with `Performance` in the same trailer block (the trailing paragraphs of `Key: value` lines). Every changed value stays within the tolerance: a euro amount by less than one cent (`|new − old| < 0.005`, taken exactly from the written decimals), every other column (`point_id`, `t`, the `pols_*` counts) only by floating-point noise (`|new − old| ≤ 1e-12 · max(|old|, |new|)`, so zero stays zero and the keys stay equal). Which `result_cf` columns are euro amounts is fixed per product in `EURO_COLUMNS` in `tools/baseline_deviations.py`: every column except `point_id`, `t` and the `pols_*` columns; `tests/test_baseline_deviations.py` pins the map to the baseline headers, so a new column fails until it is classified. `tools/baseline_deviations.py` compares every cell of each affected product's `result_cf.csv` at the commit with its first parent, lists the deviation with the largest euro and relative changes, and exits 1 with `OUT OF TOLERANCE` for a breach, a changed header or row count, an added or removed baseline, or a product missing from the map.
- **Fix forward**: a commit that repairs an earlier commit is not a revert; it names the repaired commit with its full SHA:

  ```text
  Fixes: 0123456789abcdef0123456789abcdef01234567
  ```

  The repaired commit stays in the history, as the README's rules for the history require.

## Measuring rules

Rules for a story or experiment that measures speed (`tools/measure_marginal.py`), learnt in epic-night-run and epic-parameter-files:

- **A rise above 10 % is reasoned with a control.** If a product's `t_marginal` on the branch lies more than 10 % above `main` (epic-night-run, N4), the rise is explained only with alternating runs of a `main` control in the same session: a worktree of `main` (`git worktree add /tmp/<story>-main main`), the same command run in turn on the branch and in the worktree, at least three times each, `uptime` before every run. The plan records the figures of every run and the load average they ran at. A rise that stays within the control's own spread is noise; one beyond it has a cause to name before the commit lands.
- **A forecast plan provides the controls from the start.** A plan that measures a forecast (`tools/measure_marginal.py`) provides from the start targeted alternating control runs per product: the `main` worktree and the run order of the rule above, planned for every product, and run for every product whose `t_marginal` rises above 10 %, not only for the one first noticed (epic-parameter-files, entry 13; retrospective A10).
- **Every measured figure carries its load average**, the `uptime` taken just before the run; a figure without one cannot reason a rise (N4); older figures without one are compared only with that caveat stated.
- **A failing test is recorded with its name** in the plan, and whether it passed on rerun; "one flaky test" is not a record.
- **Measure again after a review patch that touches a timed path.** A figure stands only for the code it was measured on; a patch to a cell, the runner or the export after the measurement makes the figure stale, and the measurement is repeated on the patched code before it is recorded.
- **A commit harvested from an experiment gets a story's checks.** A commit carried over from a time-boxed experiment branch passes the same mutation-domain check as a story's commit: no business logic moves out of `Projection` (epic-night-run, N1), where mutants could no longer reach it. The harvested commit is cited by its SHA on `main`, not by its SHA on the experiment branch, which other clones do not have.

## Override reason

A product cell that redefines a cell of a core base is an override. Its docstring carries one line with the reason and the document that gives it:

```python
def model_point():
    """The selected model point as a dict by column.

    Override reason: <reason>, <doc ref>
    """
```

The line starts with `Override reason:` and is not empty after the colon. `tests/test_core.py` loads every product that has a core base and fails, naming product and cell, for an override without it. A cell that the product does not define is inherited and needs no reason.

## Changed files in `UPSTREAM.md`

The hash table of a product's `UPSTREAM.md` stays upstream's: it lists every copied file with its upstream SHA-256, also after phase 3 changes the file. A product whose folder phase 3 changes gets a section below the hash table that names every changed file and every added symlink:

```markdown
## Changed in phase 3

| Path | Change |
|---|---|
| `RLV_DE_S/Projection/__init__.py` | `_bases` names `.CoreProjection`; inherited from the core: `model_point`, …; overrides the core: `lapse_factor` (cover expires in the final policy year), …; renamed: `proj_start` → `t_start`, now inherited, …; References removed, their values items of `param_tariff_type.csv` (`sex_mix_male` → `unisex_mix_male`, …) or the core file, `rechnungszins` a model-point column; every parameter read goes through `data.param` |
| `RLV_DE_S/CoreProjection` | added: symlink to the core space folder `core/Core/Projection` |
```

`tests/test_provenance.py` skips the hash check for a listed file, requires every listed changed file to stay in the hash table, and requires every symlink in a product folder to be listed and to resolve to a core space folder under `core/`. A changed file that is not listed fails the hash check as before.

A row states the end state: the file as it is now against upstream, the import commit `c23e22e`, whose files the hash table's rows match (`git show c23e22e:products/<product>/<path>`). It names what is renamed, removed, added or holds another value than upstream, and no interim state: a name added and later removed, a file renamed twice or an item moved twice appears only as where it is now. A name in a row is a current name; an upstream name stands only as the old side of a rename (`old` → `new`) or in a "was" or "renamed from" phrase. A commit that changes a listed file rewrites its row to the new end state rather than appending to it; how the file got there is its history in git (`git log c23e22e.. -- products/<product>/<path>`). One row per path, the path in backticks; the intro paragraph above the table says the same of the whole folder. The facts a row states follow the kind of file:

- a space's `__init__.py` (`Projection`, `Data`): its `_bases`, then its cells and References by class, read off upstream's file, the current one and the core space's `core/Core/<Space>/__init__.py`: renamed (`old` → `new`); inherited from the core, removed here; overriding the core, each with a short reason condensed from the cell's `Override reason:` line; added product-only; the References removed, with the file now holding their item (`param_tariff_type.csv` or `core/Core/Data/param_core.csv`). The changes in the bodies of the kept cells are a few sentences by class ("every parameter read goes through `data.param`"), not one per cell or per commit;
- a CSV file: its columns or items renamed, removed and added, and every value that differs from upstream with its basis (the acceptance or decision that set it);
- a document or script (`model.md`, `technical-notes.md`, `sources.md`, `product-spec.md`, `run.py`, the model's `__init__.py`): "names follow the renames above", and the changes of content against upstream: sections added, figures recomputed, values changed;
- an added file: what it holds and where its rows came from.

As a rule a product adds no regular file, since an added file has no upstream hash; the paths phase 3 adds are symlinks to core space folders. The exceptions are the parameter and frequency tables. Every product has its tariff-type file `param_tariff_type.csv` (section "The parameter files"), read through the Reference `param_file` of its `Data`: RV's is upstream's `param_table.csv` renamed, Pflege's merges upstream's `basis_table.csv` and `expense_table.csv`, the other eight are new, their rows the scalar References and literals that moved out of the code. Nine products hold their premium payment frequencies in `prem_freq_table.csv` (section "Contract data and charges"): BU, Index, KLV, RV, Riester and RLV renamed from an upstream frequency table, Basis' the frequency rows of its `option_table.csv`, FRV's and Pflege's the frequencies their code held as literals; Sofort holds its annuity payment frequencies in `ann_freq_table.csv` (section "Formula literals"). A file renamed or merged is listed with two kinds of change, as Pflege's merge:

```markdown
| `param_tariff_type.csv` | added: merged from `basis_table.csv` and `expense_table.csv` … |
| `basis_table.csv` | removed: merged into `param_tariff_type.csv` |
| `expense_table.csv` | removed: merged into `param_tariff_type.csv` |
```

A change starting `added:` that is no symlink names a regular file that must be present and is not in the hash table. A change starting `removed:` names a file of the hash table that must be absent; its row with upstream's hash stays. A product switched to the table factory lists its mortality file so (Index' `mort_table.csv`, BU's `mortality_table.csv`, RV's `mort_table.csv`, KLV's `mort_table.csv`, FRV's `mort_table.csv`, RLV's `mort_table.csv`, Basis' `mort_table.csv`), and the count of copied files in `tests/test_provenance.py` stays upstream's. The folder then holds exactly the hash table's files without the removed ones, plus the added ones and `UPSTREAM.md`.
